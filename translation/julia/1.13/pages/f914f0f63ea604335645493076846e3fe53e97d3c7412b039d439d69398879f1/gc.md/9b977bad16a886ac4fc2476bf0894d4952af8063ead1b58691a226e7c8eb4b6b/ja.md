# Garbage Collection in Julia

## Introduction

Julia は、非移動型で、一部並行処理に対応した並列世代別の、ほぼ正確なマーク・スイープ型ガベージコレクターを備えています（C から Julia を呼び出すユーザー向けに、スタックを保守的に走査するインターフェースもオプションとして提供されています）。

## Allocation

Julia では、割り当て要求のサイズに応じて使い分ける 2 種類のアロケーターを使用します。2 KiB 以下のオブジェクトはスレッドごとのフリーリストプールアロケーターで割り当てられ、2 KiB を超えるオブジェクトは libc の malloc を通じて割り当てられます。

Julia のプールアロケーターは、オブジェクトをサイズクラスごとに分けます。そのため、プールアロケーターが管理するメモリページ（64 ビットプラットフォームでは OS のページ 4 個分）には、同じサイズクラスのオブジェクトだけが格納されます。プールアロケーターの各メモリページには、スレッドごとのロックフリーリストに格納されたページメタデータが対応付けられています。このメタデータには、そのページに生存オブジェクトがあるかどうか、空きスロットの数、ページ内のフリーリストにある最初と最後のオブジェクトへのオフセットなどの情報が含まれます。たとえば、生存オブジェクトがまったくないページは走査せずに OS に返却できるため、このメタデータを使ってコレクションフェーズを効率化できます。

オブジェクトのないページは OS に返却できますが、対応するメタデータは恒久的に割り当てられ、そのページより長く存続する場合があります。前述のとおり、割り当て済みページのメタデータはスレッドごとのロックフリーリストに格納されます。一方、空きページのメタデータは、ページがマップ済みだが未アクセスの場合（`page_pool_clean`）、遅延スイープ済みでバックグラウンド GC スレッドによる madvise を待っている場合（`page_pool_lazily_freed`）、または madvise 済みの場合（`page_pool_freed`）に応じて、3 つの別々のロックフリーリストのいずれかに格納されます。

Julia のプールアロケーターは、「段階的な」割り当て方式を採用しています。プールアロケーター用のメモリページを要求すると、Julia は次のように処理します。

  * `page_pool_lazily_freed` からページの取得を試みます。このリストには、直近の stop-the-world フェーズで空だったものの、並行スイーパー GC スレッドによる madvise がまだ行われていないページが含まれます。
  * `page_pool_lazily_freed` からページを取得できなかった場合は、`page_pool_clean` からの取得を試みます。このリストには、以前のページ割り当て要求時に mmap されたものの、まだアクセスされていないページが含まれます。
  * `pool_page_clean` と `page_pool_lazily_freed` のどちらからもページを取得できなかった場合は、`page_pool_freed` からの取得を試みます。このリストには、並行スイーパー GC スレッドによる madvise がすでに行われ、基盤となる仮想アドレスを再利用できるページが含まれます。
  * 上記のすべての試行に失敗した場合は、ページをまとめて mmap し、そのうち 1 ページを取得して、残りのページを `page_pool_clean` に挿入します。

## Marking and Generational Collection

Julia のマークフェーズは、オブジェクトグラフに対する並列反復型深さ優先探索として実装されています。Julia のコレクターは非移動型であるため、オブジェクトの世代情報を、そのオブジェクトが存在するメモリ領域だけから判定することはできません。オブジェクトヘッダーまたはサイドテーブルに何らかの形で記録する必要があります。オブジェクトヘッダーの下位 2 ビットは、それぞれ、マークフェーズでオブジェクトを走査した際にセットされるマークビットと、世代別コレクション用の世代ビットに使われます。

世代別コレクションはスティッキービットによって実装されています。マークビットがセットされていないオブジェクトだけがマークスタックに積まれ、トレースされます。オブジェクトが最古世代に達すると、いわゆる「クイックスイープ」ではマークビットがリセットされません。そのため、後続のマークフェーズではこれらのオブジェクトはトレースされません。一方、「フルスイープ」ではすべてのオブジェクトのマークビットがリセットされるため、後続のマークフェーズですべてのオブジェクトがトレースされます。オブジェクトは、スイープフェーズを生き残るたびに次の世代へ昇格します。ミューテーター側では、フィールドへの書き込みをライトバリアで捕捉します。書き込み対象のオブジェクトが最終世代にあり、書き込まれるフィールドのオブジェクトが最終世代にない場合、ライトバリアはそのオブジェクトのアドレスをスレッドごとの記憶集合に追加します。この記憶集合内のオブジェクトは、マークフェーズでトレースされます。

## Sweeping

Julia のオブジェクトプールのスイープには、2 つの種類があります。プールアロケーターが管理するページに生存オブジェクトが 1 つ以上ある場合は、死んだオブジェクトをつないでフリーリストを作成する必要があります。ページに生存オブジェクトがまったくない場合は、たとえば Linux の madvise システムコールを使って、そのページの物理メモリを OS に返却できます。

前者のスイープはワークスティーリングによって並列化されます。後者については、`--gcthreads=X,1` フラグでページの並行スイープが有効になっている場合、ミューテータースレッドと並行して、バックグラウンドスイーパー・スレッドで madvise システムコールを実行します。コレクターの stop-the-world フェーズでは、生存オブジェクトを含まないプール割り当てページが、まず `pool_page_lazily_freed` に追加されます。その後、バックグラウンドスイープスレッドが起動し、`pool_page_lazily_freed` からページを取り出して madvise を呼び出し、`pool_page_freed` に挿入します。前述のとおり、`pool_page_lazily_freed` はミューテータースレッドとも共有されています。そのため、割り当て負荷の高いマルチスレッド処理では、ミューテータースレッドは `pool_page_lazily_freed` 内のページから直接割り当てることで、新しい mmap 済みページや madvise 済みページへのアクセスに伴うページフォールトを回避できることがよくあります。その一方で、バックグラウンドスイーパー・スレッドが madvise するページ数は、ミューテーターがすでに取得したページがある分だけ少なくなります。

## Heuristics

GC ヒューリスティクスは、ガベージコレクション間の割り当て間隔の大きさを変えることで GC を調整します。

GC ヒューリスティクスは、コレクション後のヒープサイズを測定し、https://dl.acm.org/doi/10.1145/3563323, が説明するアルゴリズムに従って次回のコレクションを設定します。要約すると、このアルゴリズムでは、ヒープの目標サイズは生存ヒープサイズの平方根に比例し、GC がオブジェクトを解放する速度とミューテーターが割り当てを行う速度に応じて調整されるべきだとしています。ヒープサイズは、使用中のページ数と malloc を使うオブジェクト数を数えて測定します。以前は生存オブジェクト数を数えてヒープサイズを測定していましたが、この方法では断片化が考慮されず、判断を誤る可能性があります。また、スレッドローカルな情報（割り当て数）を使って、プロセス全体に関わる判断（GC を実行するタイミング）を行っていました。ページ数を測定する方法なら、判断をグローバルに行えます。

ヒープサイズが許容最大サイズの 80% に達すると、GC はフルコレクションを実行します。
