# Julia Functions

この文書では、関数、メソッド定義、メソッドテーブルの仕組みを説明します。

## Method Tables

Juliaの関数はすべてジェネリック関数です。ジェネリック関数は概念上は1つの関数ですが、多数の定義、すなわちメソッドから構成されます。ジェネリック関数のメソッドは、メソッドテーブルに格納されます。グローバルなメソッドテーブルは1つだけあり、型は`MethodTable`、名前は`Core.methodtable`です。呼び出しなど、メソッドに対するデフォルトの操作はすべてこのテーブルを使用します。

## [Function calls](@id Function-calls)

`f(x, y)`という呼び出しでは、次の手順が実行されます。まず、タプル型`Tuple{typeof(f), typeof(x), typeof(y)}`が構築されます。最初の要素が関数自体の型であることに注意してください。これは、メソッドの検索において、関数自体もほかの引数と対等に扱われるためです。このタプル型を使って、グローバルなメソッドテーブルを検索します。ただし、検索結果はシステムがキャッシュできるため、後で同様の検索を行う際には、これらの手順を省略できます。

このディスパッチ処理は`jl_apply_generic`によって実行されます。これは2つの引数を取ります。1つは値`f`、`x`、`y`を格納した配列へのポインター、もう1つは値の個数（この場合は3）です。

システム全体を通じて、関数と引数リストを扱うAPIには2種類あります。関数と引数を別々に受け取るものと、単一の引数構造を受け取るものです。前者では、関数は別に渡されるため、「引数」の部分に関数の情報は*含まれません*。後者では、引数構造の最初の要素が関数です。

たとえば、呼び出しを実行する次の関数は`args`ポインターだけを受け取るため、args配列の最初の要素が呼び出す関数になります。

```c
jl_value_t *jl_apply(jl_value_t **args, uint32_t nargs)
```

同じ機能を提供する次のエントリーポイントは関数を別に受け取るため、`args`配列に関数は含まれません。

```c
jl_value_t *jl_call(jl_value_t *f, jl_value_t **args, int32_t nargs);
```

## Adding methods

上記のディスパッチ処理を踏まえると、新しいメソッドを追加するために概念上必要なのは、(1) タプル型と、(2) メソッド本体のコードだけです。この操作は`jl_method_def`に実装されています。

## Creating generic functions

すべてのオブジェクトは呼び出し可能なので、ジェネリック関数の作成に特別な仕組みは必要ありません。そのため、`jl_new_generic_function`は単に`Function`の新しいシングルトンサブタイプ（サイズ0）を作成し、そのインスタンスを返します。関数には、デバッグ情報やオブジェクトの表示に使われる、覚えやすい「表示名」を付けることができます。たとえば、`Base.sin`の名前は`sin`です。慣例として、作成される*型*の名前は、関数名の先頭に`#`を付けたものになります。したがって、`typeof(sin)`は`Base.#sin`となります。

## Closures

クロージャは、キャプチャした変数に対応するフィールド名を持つ、呼び出し可能なオブジェクトにすぎません。たとえば、次のコードは、

```julia
function adder(x)
    return y->x+y
end
```

おおよそ次のような形に低水準化されます。

```julia
struct ##1{T}
    x::T
end

(_::##1)(y) = _.x + y

function adder(x)
    return ##1(x)
end
```

## Constructors

コンストラクター呼び出しは、型に対する呼び出し、つまり`Type{T}`上で定義されたメソッドの呼び出しにすぎません。

## Builtins

`Core`モジュールで定義されている「組み込み」関数は次のとおりです。

```@eval
function lines(words)
    io = IOBuffer()
    n = 0
    for w in words
        if n+length(w) > 80
            print(io, '\n', w)
            n = length(w)
        elseif n == 0
            print(io, w);
            n += length(w)
        else
            print(io, ' ', w);
            n += length(w)+1
        end
    end
    takestring!(io)
end
import Markdown
[string(n) for n in names(Core;all=true)
    if getfield(Core,n) isa Core.Builtin && nameof(getfield(Core,n)) === n] |>
    lines |>
    s ->  "```\n$s\n```" |>
    Markdown.parse
```

これらの大半はシングルトンオブジェクトで、その型はすべて`Builtin`のサブタイプです。この型自体は`Function`のサブタイプです。これらの目的は、「jlcall」呼び出し規約を使うランタイムのエントリーポイントを公開することです。

```c
jl_value_t *(jl_value_t*, jl_value_t**, uint32_t)
```

## Keyword arguments

キーワード引数は、kwcall関数にメソッドを追加することで実現されます。この関数は通常「キーワード引数ソーター」または「キーワードソーター」と呼ばれ、匿名で定義された関数の内部本体を呼び出します。kwsorter関数の各定義は、通常のメソッドテーブル内にあるいずれかの定義と同じ引数を取りますが、先頭に`NamedTuple`引数が1つ追加されています。この引数は、渡されたキーワード引数の名前と値を保持します。kwsorterの役割は、キーワード引数を名前に基づいて所定の位置に並べ替え、必要なデフォルト値の式を評価して補うことです。その結果、通常の位置引数リストが得られ、それがコンパイラーの生成する別の関数に渡されます。

この処理を理解するには、キーワード引数を持つメソッド定義がどのように低水準化されるかを見るのが一番です。次のコードは、

```julia
function circle(center, radius; color = black, fill::Bool = true, options...)
    # draw
end
```

実際には*3つ*のメソッド定義を生成します。1つ目は、キーワード引数も含めたすべての引数を位置引数として受け取り、メソッド本体のコードを含む関数です。この関数の名前は自動生成されます。

```julia
function #circle#1(color, fill::Bool, options, circle, center, radius)
    # draw
end
```

2つ目のメソッドは、元の`circle`関数に対する通常の定義で、キーワード引数が渡されなかった場合を処理します。

```julia
function circle(center, radius)
    #circle#1(black, true, pairs(NamedTuple()), circle, center, radius)
end
```

これは単に、デフォルト値を渡して1つ目のメソッドにディスパッチします。残余引数の名前付きタプルには`pairs`が適用され、キーと値のペアとして反復できるようになります。メソッドが残余キーワード引数を受け付けない場合、この引数は存在しないことに注意してください。

最後に、kwsorterの定義があります。

```
function (::Core.kwcall)(kws, circle, center, radius)
    if haskey(kws, :color)
        color = kws.color
    else
        color = black
    end
    # etc.

    # put remaining kwargs in `options`
    options = structdiff(kws, NamedTuple{(:color, :fill)})

    # if the method doesn't accept rest keywords, throw an error
    # unless `options` is empty

    #circle#1(color, fill, pairs(options), circle, center, radius)
end
```

## [Compiler efficiency issues](@id compiler-efficiency-issues)

関数ごとに新しい型を生成することは、Juliaの「デフォルトですべての引数について特殊化する」という設計と組み合わさると、コンパイラーのリソース使用量に深刻な影響を及ぼす可能性があります。実際、この設計の初期実装では、ビルドとテストの時間が大幅に増え、メモリー使用量も増加し、システムイメージは従来のほぼ2倍になりました。単純な実装では、システムがほとんど使い物にならなくなるほど問題が深刻になります。この設計を実用的なものにするには、いくつかの重要な最適化が必要でした。

最初の問題は、関数を値として取る引数に異なる値が渡されるたびに、関数が過剰に特殊化されることです。多くの関数は、引数を別の関数や格納先など、ほかの場所へ単に「受け渡す」だけです。このような関数を、渡される可能性のあるすべてのクロージャに対して特殊化する必要はありません。幸い、このケースは、関数が引数のいずれかを*呼び出す*かどうか（つまり、その引数がどこかで「先頭位置」に現れるかどうか）を見るだけで簡単に判別できます。`map`のような性能が重要な高階関数は、確かに引数の関数を呼び出すため、期待どおり引き続き特殊化されます。この最適化は、フロントエンドの`analyze-variables`パスで、どの引数が呼び出されるかを記録することで実装されています。`cache_method`は、`Function`の型階層に属する引数が、`Any`または`Function`として宣言されたスロットに渡されると、`@nospecialize`アノテーションが適用されているかのように動作します。このヒューリスティックは、実際に非常に効果的なようです。

次の問題は、メソッドテーブルの構造に関するものです。実証的な調査によると、動的にディスパッチされる呼び出しの大半は、引数を1つか2つ取ります。さらに、その多くは最初の引数だけを考慮すれば解決できます。（余談ですが、シングルディスパッチの支持者にとって、これはまったく意外ではないでしょう。ただし、この議論が意味するのは「多重ディスパッチは実際には最適化しやすい」ので採用すべきだということであり、「シングルディスパッチを使うべきだ」ということでは*ありません*！）そこで、メソッドテーブルとキャッシュは、左から右へたどる決定木に基づいて構造を分割し、効率的な最近傍探索を可能にしています。

フロントエンドは、すべてのクロージャに対して型宣言を生成します。当初、これは通常の型宣言を生成することで実装されていました。しかし、その結果、非常に多数のコンストラクターが生成され、しかもそのすべてが単純なもの（すべての引数をそのまま[`new`](@ref)に渡すだけ）でした。メソッドには半順序があるため、これらすべてのメソッドの挿入にはO(n²)の時間がかかります。加えて、その数が多すぎて保持しておくこと自体が負担になります。そこで、`struct_type`式を直接生成してデフォルトコンストラクターの生成を回避し、`new`を直接使ってクロージャのインスタンスを作成するように最適化しました。あまり美しい方法とはいえませんが、必要なことはやらなければなりません。

次の問題は`@test`マクロでした。このマクロは、テストケースごとに引数を取らないクロージャを生成していました。しかし、各テストケースはその場で1回実行されるだけなので、これは本来必要ありません。そこで、`@test`を変更し、テスト結果（true、false、または例外の発生）を記録して、その結果をテストスイートのハンドラーに渡して呼び出すtry-catchブロックへ展開するようにしました。
