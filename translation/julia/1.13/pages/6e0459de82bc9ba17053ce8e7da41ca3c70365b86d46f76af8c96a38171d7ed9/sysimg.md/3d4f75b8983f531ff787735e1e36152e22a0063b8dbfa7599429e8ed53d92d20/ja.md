# System Image Building

## [Building the Julia system image](@id Building-the-Julia-system-image)

Julia には、`Base` モジュールの内容を含む、`sys.ji` という名前の解析済みシステムイメージが付属しています。このファイルは、起動時間を大幅に短縮するため、可能な限り多くのプラットフォームで `sys.{so,dll,dylib}` という共有ライブラリにも事前コンパイルされています。事前コンパイル済みのシステムイメージファイルが付属しないシステムでは、Julia の `DATAROOTDIR/julia/base` フォルダーに含まれるソースファイルから生成できます。

Julia はデフォルトで、利用可能なシステムスレッド数の半分を使ってシステムイメージを生成します。これは [`JULIA_IMAGE_THREADS`](@ref JULIA_IMAGE_THREADS) 環境変数で制御できます。

この処理は、次のような複数の目的に役立ちます。

  * 事前コンパイル済みの共有ライブラリ形式のシステムイメージが付属していないプラットフォームでそれをビルドし、起動時間を短縮する。
  * `Base` を変更してシステムイメージを再ビルドし、次回 Julia を起動したときに新しい `Base` を使う。
  * パッケージをシステムイメージに含める `userimg.jl` ファイルを用意し、起動環境にパッケージを組み込んだシステムイメージを作成する。

[`PackageCompiler.jl` package](https://github.com/JuliaLang/PackageCompiler.jl) には、この処理を自動化する便利なラッパー関数が用意されています。

## [System image optimized for multiple microarchitectures](@id sysimg-multi-versioning)

システムイメージは、同じ命令セットアーキテクチャ（ISA）に属する複数の CPU マイクロアーキテクチャ向けに、同時にコンパイルできます。異なる ISA 拡張やその他のマイクロアーキテクチャ機能を活用できるよう、共有関数に最小ディスパッチポイントを挿入して、同じ関数の複数のバージョンを作成できます。実行時には、利用可能な CPU 機能に基づいて、最も高い性能を発揮するバージョンが自動的に選択されます。

### Specifying multiple system image targets

システムイメージのコンパイル時に複数のターゲットを指定すると、複数のマイクロアーキテクチャに対応したシステムイメージを有効にできます。これは、[`JULIA_CPU_TARGET`](@ref JULIA_CPU_TARGET) make オプションを使う方法と、コンパイルコマンドを手動で実行する際に `-C` コマンドラインオプションを使う方法があります。オプション文字列では、複数のターゲットを `;` で区切ります。各ターゲットは CPU 名の後に、`,` で区切った複数の機能を指定する構文です。LLVM がサポートするすべての機能を指定でき、機能名の前に `-` を付けると、その機能を無効にできます。（LLVM の構文との一貫性を保つため、`+` を前置することもできますが、無視されます。）さらに、関数のクローン作成の動作を制御するための特殊な機能もいくつかサポートされています。

!!! note
    最初のターゲット以外では、各ターゲットに `clone_all` または `base(<n>)` のいずれかを指定するのが望ましい方法です。これにより、すべての関数をクローンするターゲットと、他のターゲットを基にするターゲットが明確になります。指定しない場合、デフォルトではすべての関数をクローンせず、クローンしない関数には最初のターゲットの関数定義をフォールバックとして使用します。


1. `clone_all`

    デフォルトでは、マイクロアーキテクチャの機能による恩恵が最も大きいと見込まれる関数だけがクローンされます。ただし、ターゲットに `clone_all` を指定すると、システムイメージ内の**すべての**関数がそのターゲット向けにクローンされます。負の形式である `-clone_all` を使うと、組み込みのヒューリスティックによる全関数のクローンを防げます。
2. `base(<n>)`

    `<n>` は、0 以上の数値（例：`base(0)`、`base(1)`）を表すプレースホルダーです。デフォルトでは、一部の関数だけをクローンする（つまり `clone_all` ではない）ターゲットで関数がクローンされない場合、デフォルトターゲット（最初に指定したターゲット）の関数が使われます。`base(<n>)` オプションを指定すると、別のターゲットを基準にするよう変更できます。0 始まりで `n` 番目のターゲットが、デフォルトの `0` 番目のターゲットの代わりに基準ターゲットとして使われます。基準ターゲットには、`0` または別の `clone_all` ターゲットを指定する必要があります。`clone_all` ではないターゲットを基準ターゲットに指定すると、エラーになります。
3. `opt_size`

    実行時の性能に大きな影響がない場合に、ターゲット向けの関数をサイズ優先で最適化します。これは GCC および Clang の `-Os` オプションに相当します。
4. `min_size`

    実行時の性能に大きな影響が生じる可能性がある場合でも、ターゲット向けの関数をサイズ優先で最適化します。これは Clang の `-Oz` オプションに相当します。

たとえば、執筆時点では、julialang.org からダウンロードできる公式の `x86_64` Julia バイナリの作成に、次の文字列が使われています。

```
generic;sandybridge,-xsaveopt,clone_all;haswell,-rdrnd,base(1)
```

これにより、3 つのターゲットを持つシステムイメージが作成されます。1 つ目は汎用の `x86_64` プロセッサ向け、2 つ目は `sandybridge` ISA 向け（`xsaveopt` を明示的に除外）で、すべての関数を明示的にクローンします。3 つ目は `haswell` ISA 向けで、`sandybridge` の sysimg バージョンを基にし、`rdrnd` も除外します。Julia の実装が生成された sysimg を読み込む際、ホストプロセッサの CPU 機能フラグを確認し、可能な限り高い ISA レベルを有効にします。なお、ベースレベル（`generic`）では `cx16` 命令が必要です。この命令は一部の仮想化ソフトウェアでは無効になっているため、`generic` ターゲットを読み込むには有効にする必要があります。互換性を高めるには、代わりに `generic,-cx16` ターゲットを指定して sysimg を生成する方法もあります。ただし、一部のコードで性能や安定性に問題が生じる可能性があります。

### Implementation overview

ここでは、実装に関わる各部分を簡単に説明します。実装の詳細については、各コンポーネントのコードコメントを参照してください。

1. システムイメージのコンパイル

    解析とクローン作成の判断は `src/processor*` で行います。現在は、ループ、SIMD 命令、その他の数学演算（fastmath、fma、muladd など）の有無に基づいて関数をクローンできます。この情報は、実際にクローンを行う `src/llvm-multiversioning.cpp` に渡されます。クローン作成とディスパッチスロットの挿入（その方法については `MultiVersioning::runOnModule` のコメントを参照）に加え、このパスでは、実行時にシステムイメージを正しく読み込んで初期化できるよう、メタデータも生成します。メタデータの詳細は `src/processor.h` に記載されています。
2. システムイメージの読み込み

    システムイメージの読み込みと初期化は `src/processor*` で行います。ここでは、システムイメージの生成時に保存されたメタデータを解析します。ホストの機能検出とターゲット選択の判断は、ISA に応じて `src/processor_*.cpp` で行います。ターゲットの選択では、CPU 名の完全一致、ベクトルレジスターサイズの大きさ、機能数の多さが優先されます。この処理の概要は `src/processor.cpp` に記載されています。

## Trimming

Base には多くの機能が含まれているため、システムイメージは通常かなり大きくなります。また、利便性と後方互換性のため、デフォルトでは LinearAlgebra などのパッケージもいくつか含まれています。ほとんどのプログラムがこれらのパッケージの関数を使うのは一部だけです。そのため、未使用の関数を除外して容量を節約する「トリミング」を行い、バイナリをビルドするのが合理的です。

トリミングの基本的な考え方は妥当ですが、Julia には動的な機能やリフレクション機能があるため、一般にどの関数が未使用かを判断するのは困難（あるいは不可能）です。極端な例として、次のようなコードを考えてみてください。

```
getglobal(Base, Symbol(readchomp(stdin)))(1)
```

このコードは `stdin` から関数名を読み取り、その名前の Base 関数を値 `1` に対して呼び出します。この場合、どの関数が呼び出されるかを予測できないため、どの関数も確実に「未使用」とは見なせません。Julia 自身の REPL など、特筆すべき例外はありますが、実際のプログラムの大半はこのような処理を行いません。

それほど極端ではない例として、型が不安定なためにコンパイラーがどのメソッドが呼び出されるか予測できない場合があります。しかし、コードの型が適切に定まり、リフレクションを使っていなければ、必要なメソッドの集合を完全に、かつ（願わくば）比較的小さく特定し、残りを削除できます。`--trim` コマンドラインオプションは、この種のコンパイルを要求します。

システムイメージのビルドコマンドに `--trim` を指定すると、コンパイラーは `Base.Experimental.entrypoint` でマークされたメソッドを起点に、呼び出しをたどり始めます。呼び出しが動的すぎて、呼び出し先の候補を妥当な範囲まで絞り込めない場合は、その呼び出し箇所を示すエラーがコンパイル時に発生します。テスト目的であれば、`--trim=unsafe` または `--trim=unsafe-warn` を指定して、これらのエラーを無視できます。その場合、システムイメージはビルドされますが、必要なコードが含まれていないと実行時にクラッシュする可能性があります。

トリミング済みバイナリは完全にコンパイルされているため、Julia IR を必要としません。そのため、通常は `--strip-ir` と `--trim` を併せて指定するとよいでしょう。将来的には `--trim` によって `--strip-ir` も暗黙に有効になるようにするかもしれませんが、現時点では両者を独立したオプションとして扱っています。

バイナリを可能な限り小さくするには、`--strip-metadata` を指定し、Unix の `strip` ユーティリティを実行するのも有効です。ただし、これらの手順では、それぞれ Julia 固有のデバッグ情報とネイティブのデバッグ情報（DWARF 形式）が削除されるため、デバッグが難しくなります。

これらのオプションを手動で指定する代わりに、ほとんどのユーザーは [JuliaC.jl](https://github.com/JuliaLang/JuliaC.jl) を使ってトリミング済みバイナリをビルドするのがよいでしょう。これは `juliac` ドライバーを提供し、コンパイル、リンク、成果物のバンドルを処理します。

### Common problems

  * Base のグローバル変数 `stdin`、`stdout`、`stderr` は定数ではないため、その型は不明です。出力には、型が既知の特定の IO オブジェクトを使ってください。最も簡単な置き換え方法は、`print(x)` または `print(stdout, x)` の代わりに `print(Core.stdout, x)` を使うことです。
  * [JET.jl](https://github.com/aviatesk/JET.jl)、[Cthulhu.jl](https://github.com/JuliaDebug/Cthulhu.jl)、[SnoopCompile](https://github.com/timholy/SnoopCompile.jl) などのツールを使って型推論の失敗を特定し、修正するには [Performance Tips](@ref man-performance-tips) に従ってください。

### Compatibility concerns

Base に小さな変更を加えることで、確実にトリミングできるプログラムの範囲が大きく広がることが分かっています。しかし、そうした変更の一部は破壊的変更と見なされるため、トリミングが要求された場合にのみ適用されます（これは外部ビルドスクリプトで行われ、現在はテストスイート内の `test/trimming/juliac-buildscript.jl` で管理されています）。そのため、多くの場合、トリミングには Base や一部の標準ライブラリの新しいバリアントを明示的に有効にする必要があります。

トリミングを使う場合は、トリミング済みビルドを実行し、生成されたプログラムを十分にテストする継続的インテグレーション（CI）を設定することが重要です。幸い、プログラムが `--trim` で正常にコンパイルできれば、以前と同じように動作する可能性は非常に高いでしょう。ただし、開発を続ける中でトリミングを使ったビルドが引き続き成功することを確認するには、CI が必要です。

パッケージ作者は、自分のパッケージが「トリミングに対応している」かどうかをテストしたいと思うかもしれませんが、一般にはそれを確認できません。トリミングが機能するのは、`main()` のような具体的なエントリーポイントや、Julia の外部から呼び出すことを想定したライブラリのエントリーポイントがある場合に限られます。汎用パッケージでは、型安定性を確認する既存のテストである `@inferred` や `JET.@report_call` が、トリミングとの互換性を確認する最善の方法に近いものです。

トリミングによって、Julia のマイナーバージョン間に新たな互換性の問題も生じます。現時点では、あるバージョンの Julia でトリミングできるプログラムが、今後のすべてのバージョンでもトリミングできるとは保証できません。ただし、この種の互換性の破損はまれだと予想されます。また、今後はトリミング可能なプログラムの範囲を**広げる**ことも目指しています。
