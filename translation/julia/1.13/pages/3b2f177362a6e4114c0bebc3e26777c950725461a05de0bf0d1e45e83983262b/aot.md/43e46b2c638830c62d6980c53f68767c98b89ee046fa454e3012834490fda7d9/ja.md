# Ahead of Time Compilation

このドキュメントでは、Julia の ahead-of-time（AOT）コンパイルシステムの設計と構造について説明します。このシステムは、システムイメージやパッケージイメージの生成に使用されます。ここで説明する実装の多くは、`aotcompile.cpp`、`staticdata.c`、`processor.cpp` にあります。

## Introduction

Julia は通常、コードをジャストインタイム（JIT）でコンパイルしますが、コードを事前にコンパイルし、生成されたコードをファイルに保存することもできます。これには、次のような利点があります。

1. Julia プロセスの起動時間を短縮できる。
2. コードの実行ではなく JIT コンパイラーに費やす時間（初回実行までの時間、TTFX）を短縮できる。
3. JIT コンパイラーが使用するメモリ量を削減できる。

## High-Level Overview

以下では、ユーザーが新しい AOT モジュールをコンパイルするとき（たとえば、`using Foo` と入力したとき）に内部で実行される、エンドツーエンドのパイプラインの現時点での実装について説明します。より適切な処理方法を実装するにつれて、これらの詳細は今後変更される可能性があります。そのため、現在の実装が以下に記載するデータフローや関数と完全には一致しない場合があります。

### Compiling Code Images

まず、ネイティブコードにコンパイルする必要があるメソッドを特定します。コンパイル対象のメソッドの集合は、メソッドに渡される引数の型によって決まり、特定の型の組み合わせによるメソッド呼び出しは実行時まで判明しない場合があるため、これはコンパイル対象のコードを実際に実行しなければ行えません。この処理中に、コンパイラーが認識した正確なメソッドを後でコンパイルできるよう記録し、コンパイルトレースを生成します。

!!! note
    現在、イメージのコンパイル時には、Julia はトレースの生成を AOT コンパイルを行うプロセスとは別のプロセスで実行します。そのため、プリコンパイル中にデバッガーを使う際に影響が生じることがあります。デバッガーを使ってプリコンパイルをデバッグするには、rr デバッガーでプロセスツリー全体を記録し、`rr ps` で問題が発生したプロセスを特定してから、`rr replay -p PID` でそのプロセスだけを再生するのが最善です。


コンパイル対象のメソッドを特定したら、それらを `jl_create_system_image` 関数に渡します。この関数は、ネイティブコードをファイルにシリアライズする際に使う複数のデータ構造を準備し、メソッドの配列を `jl_create_native` に渡します。`jl_create_native` は各メソッドに対してコード生成を実行し、1 つ以上の LLVM モジュールを生成します。その後、`jl_create_system_image` が、モジュールからコード生成された内容に関する有用な情報を記録します。

次に、モジュールと、`jl_create_system_image` が記録した情報を `jl_dump_native` に渡します。`jl_dump_native` には、Julia に渡されたコマンドラインオプションに応じて、モジュールをビットコード、オブジェクト、またはアセンブリファイルにシリアライズするためのコードが含まれています。シリアライズされたコードと情報は、アーカイブとしてファイルに書き込まれます。

最後に、`jl_dump_native` が生成したアーカイブ内のオブジェクトファイルに対して、システムリンカーを実行します。この処理が完了すると、コンパイル済みコードを含む共有ライブラリが生成されます。

### Loading Code Images

コードイメージを読み込む際は、リンカーが生成した共有ライブラリをメモリに読み込みます。次に、システムイメージのデータを共有ライブラリから読み込みます。このデータには、共有ライブラリにコンパイルされた型、メソッド、コードインスタンスに関する情報が含まれています。この情報を使って、コードイメージのコンパイル時の状態にランタイムを復元します。

コードイメージがマルチバージョニングを有効にしてコンパイルされている場合、ローダーは現在のマシンで利用可能な CPU 機能に基づいて、各関数で使用する適切なバージョンを選択します。

システムイメージの場合、ほかのコードはまだ読み込まれていないため、ランタイムの状態はコードイメージのコンパイル時と同じです。一方、パッケージイメージでは、コンパイル時から環境が変わっている可能性があります。そのため、各メソッドをグローバルメソッドテーブルと照合し、引き続き有効なコードかどうかを確認する必要があります。

## Compiling Methods

### Tracing Compiled Methods

Julia には、JIT コンパイラーがコンパイルしたすべてのメソッドを記録するコマンドラインフラグ `--trace-compile=filename` があります。このフラグにファイル名を指定すると、関数のコンパイル時に、その関数が呼び出されたメソッドと引数の型を含むプリコンパイル文がファイルに出力されます。これにより、後の AOT コンパイルで使用できるプリコンパイルスクリプトが生成されます。[PrecompileTools](https://julialang.github.io/PrecompileTools.jl/stable/) パッケージには、パッケージ開発者がこの機能を簡単に活用するためのツールが用意されています。

### `jl_create_system_image`

`jl_create_system_image` は、後でランタイムの状態を復元するために必要な、Julia 固有のメタデータをすべて保存します。これには、コードインスタンス、メソッドインスタンス、メソッドテーブル、型情報などが含まれます。また、この関数はネイティブコードをファイルにシリアライズするために必要なデータ構造も準備します。最後に、`jl_create_native` を呼び出し、渡されたメソッドのネイティブコードを含む LLVM モジュールを 1 つ以上作成します。渡されたメソッドに対してコード生成を実行するのは `jl_create_native` の役割です。

### `jl_dump_native`

`jl_dump_native` は、ネイティブコードを含む LLVM モジュールをファイルにシリアライズします。モジュールに加えて、`jl_create_system_image` が生成したシステムイメージデータもグローバル変数としてコンパイルされます。このメソッドの出力は、コードとシステムイメージデータを含むビットコード、オブジェクト、またはアセンブリのアーカイブです。

ネイティブコードの出力では、`jl_dump_native` が特に時間のかかる処理の 1 つです。時間の多くは、LLVM IR の最適化とマシンコードの出力に費やされます。そのため、この関数では最適化とマシンコード出力の各処理をマルチスレッド化できます。スレッド数はモジュールのサイズに応じて決まりますが、[`JULIA_IMAGE_THREADS`](@ref JULIA_IMAGE_THREADS) 環境変数を設定すれば明示的に変更できます。デフォルトの最大スレッド数は利用可能なスレッド数の半分です。これより少ない値を設定すると、コンパイル時のピークメモリ使用量を抑えられます。

`jl_dump_native` は、Julia ローダーと連携して、複数のアーキテクチャ向けに最適化されたネイティブコードを生成することもできます。これは [`JULIA_CPU_TARGET`](@ref JULIA_CPU_TARGET) 環境変数を設定すると有効になり、最適化パイプライン内のマルチバージョニングパスによって処理されます。これをマルチスレッドで動作させるため、モジュールを各スレッドで個別に出力するサブモジュールに分割する前に、注釈付けの処理を追加します。この処理では、モジュール全体で利用できる情報を使って、異なるアーキテクチャ向けに複製する関数を決定します。注釈付けが完了すると、複製された関数が呼び出す必要のある関数は別のサブモジュールで必ず生成されるため、各スレッドは異なるアーキテクチャ向けのコードを並行して出力できます。

モジュールのシリアライズ方法に関するその他のメタデータもアーカイブに保存されます。たとえば、モジュールのシリアライズに使用したスレッド数や、コンパイルされた関数の数などです。

### Static Linking

AOT コンパイルの最後の処理では、`jl_dump_native` が生成したアーカイブ内のオブジェクトファイルに対してリンカーを実行します。これにより、コンパイル済みコードを含む共有ライブラリが生成されます。Julia はこの共有ライブラリを読み込んで、ランタイムの状態を復元できます。システムイメージのコンパイルでは、C コンパイラーが使用するネイティブリンカーを使って最終的な共有ライブラリを生成します。パッケージイメージでは、より一貫性のあるリンクインターフェースを提供するため、LLVM リンカーの LLD を使用します。

## Loading Code Images

### Loading the Shared Library

コードイメージを読み込む最初の手順は、リンカーが生成した共有ライブラリを読み込むことです。共有ライブラリのパスを指定して `jl_dlopen` を呼び出すと、この処理が行われます。この関数は共有ライブラリを読み込み、ライブラリ内のすべてのシンボルを解決します。

### Loading Native Code

まずローダーは、コンパイルされたネイティブコードが、ローダーの実行環境のアーキテクチャで有効かどうかを確認する必要があります。これは、古い CPU が認識できない命令を実行しないようにするためです。現在のマシンで利用可能な CPU 機能と、コードのコンパイル時に対象とした CPU 機能を照合して確認します。マルチバージョニングが有効な場合、ローダーは現在のマシンで利用可能な CPU 機能に基づいて、各関数で使用する適切なバージョンを選択します。マルチバージョニングされた機能セットのいずれも利用できない場合、ローダーはエラーをスローします。

マルチバージョニングパスの一部では、モジュール内のすべての関数を格納するグローバル配列が複数作成されます。この処理がマルチスレッドで実行される場合は配列の配列が作成され、ローダーがそれを、対象アーキテクチャ向けにコンパイルされたすべての関数を含む 1 つの大きな配列に再編成します。モジュール内のグローバル変数についても、同様の処理が行われます。

### Setting Up Julia State

次にローダーは、ネイティブコードの読み込みによって得られたグローバル変数と関数を使い、現在のプロセス内で Julia ランタイムの中核となるデータ構造を設定します。この設定では、Julia ランタイムに型とメソッドを追加し、キャッシュされたネイティブコードをほかの Julia 関数やインタープリターから利用できるようにします。パッケージイメージでは、各メソッドを検証し、グローバルメソッドテーブルの状態がパッケージイメージのコンパイル時の状態と一致することを確認する必要があります。特に、パッケージイメージのコンパイル時と読み込み時でメソッドの集合が異なる場合、そのメソッドは無効化され、初回使用時に再コンパイルされます。これは、パッケージがプリコンパイルされている場合とコードが直接実行される場合とで、実行時の意味が変わらないようにするために必要です。システムイメージでは、読み込み時にグローバルメソッドテーブルが空であるため、この検証は不要です。そのため、システムイメージはパッケージイメージよりも高速に読み込まれます。
