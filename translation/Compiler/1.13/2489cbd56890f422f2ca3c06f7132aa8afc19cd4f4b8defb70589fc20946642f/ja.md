```julia
ir_inline_unionsplit!
```

この関数の主な目的は、union-split のディスパッチ候補のシグネチャに対応するフラットな `isa` チェックを生成し、ディスパッチの動作をエミュレートすることです。これらのチェックにより、それぞれの `isa` 条件ブロック内にメソッド本体をインライン展開できます。

このエミュレーションを正しく機能させるには、次の2つの前提条件が必要です。

1. ディスパッチ候補の順序

ディスパッチ候補は、特異性の高い順に処理する必要があります。生成される `isa` チェックには、この順序を反映させなければなりません。特に、メソッドシグネチャが具象型とは限らないためです。たとえば、次のメソッドがあるとします。

```julia
f(x::Int)    = ...
f(x::Number) = ...
f(x::Any)    = ...
```

呼び出し箇所 `f(x::Any)` に対する、`isa` に基づく正しいディスパッチエミュレーションは、次のようになります。

```julia
if isa(x, Int)
    [inlined/resolved f(x::Int)]
elseif isa(x, Number)
    [inlined/resolved f(x::Number)]
else
    [inlined/resolved f(x::Any)]
end
```

`ml_matches` は、マッチしたメソッド候補をすでに正しくソートしているはずです。ただし、曖昧なケースは除きます。そうしたケースは、この段階ですでに除外しています。

2. 型の等価性制約

型変数によって課される型の等価性制約も考慮する必要があります。単純な `isa` チェックだけでは、場合によっては意味を正しく表現できません。たとえば、次のメソッド定義があるとします。

```julia
g(x::T, y::T) where T<:Integer = ...
```

この場合、呼び出し箇所 `g(x::Any, y::Any)` を次のように最適化するのは *不正* です。

```julia
if isa(x, Integer) && isa(y, Integer)
    [inlined/resolved g(x::Integer, y::Integer)]
else
    g(x, y) # fallback dynamic dispatch
end
```

`x` と `y` が同じ型であることも確認する必要があるためです。

ただし、この段階では主に `case.sig::UnionAll` を除外することで、こうしたケースをすでに除外しています。そのため、ここで型の等価性を気にする必要はありません。

要するに、`ml_matches` での検出後も候補の順序が変わらないと仮定すれば、ディスパッチ候補を順番に処理できます。
