```julia
__has_internal_change(version_or::VersionNumber, change_name::Symbol)
```

一部のJuliaパッケージは、Juliaの内部機能（たとえば、内部のJuliaデータ構造のイントロスペクション）に依存していることが知られています。こうしたパッケージとJuliaを並行して開発しやすくするため、`change_name`がベストエフォートで、または明示的な要求に応じて割り当てられます。この`change_name`を使うと、特定のプレリリースビルドに特定の変更が含まれているかどうかを確認できます。具体的には、現在のJuliaビルドに`version_or`向けに予定されている変更が含まれているかを、この関数で確認します。現在のバージョンが`version_or`より新しい場合、またはその変更を含むプレリリースビルドを実行している場合に、変更が含まれていると判定されます。

この仕組みを使う方法は、コミット番号に基づく`VERSION`の比較よりも優れています。プレリリース段階では複数のブランチが並行して活発に開発されるため、コミット番号による比較は不安定になり得るからです。

変更の一覧は、リリースプロセス中に次の2回クリアされます。

1. 最初のアルファ版のリリース時
2. 最初のリリース候補版のリリース時

リリース候補版やバグ修正版のリリース中に、新しい`change_name`が追加されることはありません（したがって、リリース済みのバージョンでは変更の一覧は常に空になり、`__has_internal_change`は常にバージョン比較と同等になります）。

# Example

Juliaバージョン`v"1.12.0-DEV.173"`では、行番号のデバッグ情報の内部表現が変更されました。複数のデバッグ用パッケージがこの情報を表示するための独自コードを持っているため、それに合わせて変更する必要があります。これまでの慣例では、次のようにして対応することがよくありました。

```julia
@static if VERSION > v"1.12.0-DEV.173"
    # Code to handle new format
else
    # Code to handle old format
end
```

しかし、こうしたチェックはVERSION番号が割り当てられるまで導入できません（その時点で、すべてのナイトリーユーザーにも変更が自動的に反映されます）。そのため、必然的に動作しない期間が生じていました。`__has_internal_change`を使えば、代わりに次のように記述できます。

```julia
@static if __has_internal_change(v"1.12-alpha", :invertedlinenames)
    # Code to handle new format
else
    # Code to handle old format
end
```

第1引数に指定する適切なバージョンを調べるには、`Base.__next_removal_version`を使います。これは、変更の一覧が次にクリアされるバージョン番号に設定されています。

この方法の主な利点は、ナイトリービルドで問題が発生する前に、新しいバージョンのパッケージにタグを付けてリリースできることです。これにより、ナイトリーユーザーもパッケージを継続して利用できます。

!!! warning
    この機能は、Juliaの内部機能を利用するパッケージの開発者を支援することを目的としています。絶対に必要な場合を除き、内部機能の利用は明示的に推奨されていません。また、利用する場合はパッケージが動作しなくなる可能性を理解しておく必要があります。特に、これは汎用的な機能検出の仕組みではなく、Juliaの内部機能に依存するパッケージを破壊することが判明している（または判明した）変更について、関係者間の調整を支援するための簡易的な仕組みにすぎません。
