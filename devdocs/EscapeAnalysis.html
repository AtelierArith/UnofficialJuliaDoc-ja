EscapeAnalysis

Compiler.EscapeAnalysisは、Julia's SSA-form IR（別名IRCode）のエスケープ情報を解析するためのコンパイラユーティリティモジュールです。

このエスケープ解析の目的は次のとおりです。

  • Juliaの高水準な意味論を活用し、特にプロシージャ間呼び出しを通じたエスケープやエイリアシングを推論する
  • alias-aware SROA、early finalize insertion、copy-free ImmutableArray construction、可変オブジェクトのスタック割り当てなど、さまざまな最適化に利用できる汎用性を備える
  • 完全な後向きデータフロー解析の実装と、直交する格子の性質を組み合わせた新しい格子設計に基づき、シンプルに実装する

各呼び出し引数とSSA文の横に表示される記号は、次の意味を表します。

  • ◌（通常表示）：この値のエスケープ情報は利用されないため、解析対象ではありません（たとえば、オブジェクトがisbitstypeの場合）
  • ✓（緑またはシアン）：この値はエスケープしません（has_no_escape(result.state[x])が成立）。引数エスケープもある場合は青色で表示されます（has_arg_escape(result.state[x])が成立）
  • ↑（青または黄色）：この値は戻り値を通じて呼び出し元へエスケープする可能性があります（has_return_escape(result.state[x])が成立）。未処理の例外エスケープもある場合は黄色で表示されます（has_thrown_escape(result.state[x])が成立）
  • X（赤）：この値は、グローバルメモリへのエスケープなど、エスケープ解析で推論できない場所へエスケープする可能性があります（has_all_escape(result.state[x])が成立）
  • *（太字）：この値のエスケープ状態は、ReturnEscapeとAllEscapeの間にあります（EscapeInfoの半順序において）。未処理の例外エスケープもある場合は黄色で表示されます（has_thrown_escape(result.state[x])が成立）
  • ′：この値のAliasInfoプロパティには、オブジェクトのフィールドや配列要素に関する追加情報があります

各呼び出し引数とSSA値のエスケープ情報は、次のようにプログラムから調べられます。

julia> result.state[Core.Argument(3)] # get EscapeInfo of `s2`ArgEscape
julia> result.state[Core.SSAValue(3)] # get EscapeInfo of `r3`NoEscape′

Analysis Design

Lattice Design

EscapeAnalysisは、data-flow analysisとして実装されており、x::EscapeInfoの格子上で動作します。この格子は、次のプロパティで構成されます。

  • x.Analyzed::Bool：形式上は格子の一部ではなく、xが解析済みかどうかだけを示します
  • x.ReturnEscape::BitSet：xが戻り値を通じて呼び出し元へエスケープする可能性のあるSSA文を記録します
  • x.ThrownEscape::BitSet：xが例外としてスローされる可能性のあるSSA文を記録します（後述するexception handlingで使用）
  • x.AliasInfo：xのフィールドや配列要素にエイリアスされる可能性のある値をすべて保持します（後述するalias analysisで使用）
  • x.ArgEscape::Int（未実装）：引数のsetfield!を通じて呼び出し元へエスケープすることを示します

入力プログラムの文数が有限であるという不変条件（Juliaの意味論によって保証されます）のもとでは、これらの属性を組み合わせて有限の高さを持つ半順序格子を構成できます。この格子設計の巧妙な点は、各格子プロパティを個別に扱えるため、格子演算をよりシンプルに実装できることです[LatticeDesign]。

Backward Escape Propagation

このエスケープ解析の実装は、論文[MM02]で説明されているデータフローアルゴリズムに基づいています。解析ではEscapeInfoの格子を使い、未解析のSSA文に対応するプログラムカウンタを保持する（概念上の）作業集合を管理しながら、すべての格子要素が不動点に収束するまで、格子要素を底から上へ遷移させます。解析は、各引数とSSA文のEscapeInfoを追跡する単一のグローバル状態を管理します。ただし、ある程度のフロー感度は、EscapeInfoのReturnEscapeプロパティに記録されたプログラムカウンタによって表現されている点にも注意してください。必要に応じて、後から支配関係解析と組み合わせ、フロー感度を推論できます。

このエスケープ解析の特徴的な設計の一つは、完全な後向き解析であることです。つまり、エスケープ情報は使用箇所から定義へ流れます。たとえば、以下のコード片では、EAはまず文return %1を解析し、%1（objに対応）にReturnEscapeを課します。次に%1 = %new(Base.RefValue{Base.RefValue{String}, _2}))を解析し、%1に課されたReturnEscapeを、呼び出し引数_2（sに対応）へ伝播します。

julia> code_escapes((Base.RefValue{String},)) do s
           obj = Ref(s)
           return obj
       end#5(↑ s::Base.RefValue{String}) in Main at REPL[1]:2
↑′ 1 ─ %1 = %new(Base.RefValue{Base.RefValue{String}}, _2)::Base.RefValue{Base.RefValue{String}}
◌  └──      return %1

重要なのは、この後向き解析では、エスケープ情報が制御フローではなく、使用・定義チェーンに沿って自然に流れることです[BackandForth]。その結果、エスケープ解析をシンプルに実装できます。たとえばPhiNodeは、PhiNodeに課されたエスケープ情報を、その先行値へ伝播するだけで処理できます。

julia> code_escapes((Bool, Base.RefValue{String}, Base.RefValue{String})) do cnd, s, t
           if cnd
               obj = Ref(s)
           else
               obj = Ref(t)
           end
           return obj
       end#8(✓ cnd::Bool, ↑ s::Base.RefValue{String}, ↑ t::Base.RefValue{String}) in Main at REPL[1]:2
◌  1 ─      goto #3 if not _2
↑′ 2 ─ %2 = %new(Base.RefValue{Base.RefValue{String}}, _3)::Base.RefValue{Base.RefValue{String}}
◌  └──      goto #4
↑′ 3 ─ %4 = %new(Base.RefValue{Base.RefValue{String}}, _4)::Base.RefValue{Base.RefValue{String}}
↑′ 4 ┄ %5 = φ (#2 => %2, #3 => %4)::Core.PartialStruct(Base.RefValue{Base.RefValue{String}}, Union{Nothing, Bool}[0], Any[Base.RefValue{String}])
◌  └──      return %5

Alias Analysis

EscapeAnalysisは、オブジェクトのフィールドに課されるエスケープを一定の精度で推論するため、後向きのフィールド解析を実装しています。この目的で、x::EscapeInfoのx.AliasInfoプロパティが使われます。このプロパティは、「使用箇所」でxのフィールドにエイリアスされる可能性のある値をすべて記録し、その後「定義箇所」で、記録された値のエスケープ情報を実際のフィールド値へ伝播します。具体的には、getfield呼び出しを解析して、オブジェクトのフィールドにエイリアスされる可能性のある値を記録し、%new(...)式またはsetfield!呼び出し[Dynamism]を解析する際に、その値のエスケープ情報をフィールドへ伝播します。

julia> code_escapes((String,)) do s
           obj = SafeRef("init")
           obj[] = s
           v = obj[]
           return v
       end#11(✓ s::String) in Main at REPL[1]:2
◌  1 ─     return _2

上の例では、%3（vに対応）に課されたReturnEscapeは、%1（objに対応）へ直接伝播するのではなく、ReturnEscapeだけが_2（sに対応）へ伝播します。ここでは、%3が%1のAliasInfoプロパティに記録されます。これは、%1の第1フィールドにエイリアスされる可能性があるためです。その後、Base.setfield!(%1, :x, _2)::Stringを解析すると、そのエスケープ情報は_2へ伝播しますが、%1へは伝播しません。

つまり、EscapeAnalysisは、オブジェクトのフィールドのエスケープを解析するため、getfield-%new/setfield!チェーンをまたいで、どのIR要素がエイリアスされるかを追跡します。しかし、このエイリアス解析は、ほかのIR要素も扱えるよう一般化する必要があります。Julia IRでは、同じオブジェクトが異なるIR要素で表されることがあるため、実際には同じオブジェクトを表し得るIR要素どうしで、同じエスケープ情報を共有する必要があるからです。PiNodeやtypeassertのように、オペランドの値をそのまま返すIR要素は、IRレベルのエイリアシングを引き起こす可能性があります。そのため、こうしたエイリアス値のいずれかに課されたエスケープ情報は、値どうしで共有する必要があります。さらに、PhiNodeへの変更を正しく推論するうえでも、この処理が必要です。次の例を考えてみましょう。

julia> code_escapes((Bool, String,)) do cond, x
           if cond
               ϕ2 = ϕ1 = SafeRef("foo")
           else
               ϕ2 = ϕ1 = SafeRef("bar")
           end
           ϕ2[] = x
           y = ϕ1[]
           return y
       end#14(✓ cond::Bool, ✓ x::String) in Main at REPL[1]:2
◌  1 ─      goto #3 if not _2
✓′ 2 ─ %2 = %new(Main.SafeRef{String}, "foo")::Main.SafeRef{String}
◌  └──      goto #4
✓′ 3 ─ %4 = %new(Main.SafeRef{String}, "bar")::Main.SafeRef{String}
✓′ 4 ┄ %5 = φ (#2 => %2, #3 => %4)::Main.SafeRef{String}
✓′ │   %6 = φ (#2 => %2, #3 => %4)::Main.SafeRef{String}
◌  │          builtin Base.setfield!(%5, :x, _3)::String
✓  │   %8 =   builtin Base.getfield(%6, :x)::String
◌  └──      return %8

ϕ1 = %5とϕ2 = %6はエイリアスされているため、%8 = Base.getfield(%6, :x)::String（y = ϕ1[]に対応）に課されたReturnEscapeは、Base.setfield!(%5, :x, _3)::String（ϕ2[] = xに対応）にも伝播する必要があります。このエスケープ情報を正しく伝播するには、ϕ1とϕ2の先行値もエイリアスされる可能性があると認識し、それらのエスケープ情報を同一化する必要があります。

このようなエイリアス情報の興味深い性質として、「使用箇所」では分からず、「定義箇所」でしか導出できない点があります（エイリアシングは概念上、代入と等価です）。そのため、後向き解析には自然には適合しません。関連する値の間でエスケープ情報を効率よく伝播するため、EscapeAnalysis.jlは、古いJVMの論文[JVM05]で説明されているエスケープ解析アルゴリズムに着想を得た手法を使います。つまり、エスケープ格子要素の管理に加えて、「同値」エイリアス集合も管理します。これは、エイリアスされた引数とSSA文をまとめた互いに素な集合です。この集合は、互いにエイリアスされる可能性のある値を管理し、そのいずれかに課されたエスケープ情報を値どうしで同一化します。

ReturnEscapeは%2（SafeRef(s)に対応）にのみ課され、%4（SafeRef(t)に対応）には課されない点に注意してください。これは、割り当てられた配列の次元と、すべてのarrayref/arrayset操作で使われるインデックスが定数情報として得られるためです。EscapeAnalysisは、%6が%2にエイリアスされる一方、%4には決してエイリアスされないと推論できます。このような場合、後続の最適化パスでBase.arrayref(true, %1, 1)::Anyを%2に置き換えられます（「ロード転送」とも呼ばれます）。最終的には、配列%1の割り当てを完全に除去できます（「スカラー置換」とも呼ばれます）。

オブジェクトフィールドの解析では、型推論から得られる型情報を使ってフィールドへのアクセスを簡単に解析できます。一方、配列の次元は型情報に含まれないため、その情報を導出する追加の解析が必要です。現時点でEscapeAnalysisは、まず単純な線形走査を追加で行って割り当てられた配列の次元を解析し、その後メインの解析ルーチンを実行します。これにより、後続のエスケープ解析で配列操作を正確に解析できます。

ただし、このような正確な「要素ごと」のエイリアス解析は難しいことがよくあります。配列に固有の主な難しさは、配列の次元やインデックスが定数でないことが多い点です。

  • ループによって、ループごとに変化する非定数の配列インデックスが生成されることが多い
  • （ベクトルに固有の問題として）配列のリサイズによって次元が変わり、定数性が失われる

具体例を使って、これらの難しさを見ていきましょう。

こうした問題に対処するには、推論で配列の次元を扱い、フロー感度を保って次元情報を伝播する必要があります[ArrayDimension]。また、ループごとに変化する値を適切に表現する方法も必要です。

現時点でEscapeAnalysisは、配列の次元やインデックスが自明に非定数である場合、インデックスの正確な情報を追跡しない、より不正確な解析へすぐに切り替えます。この切り替えは、データフロー解析フレームワークにおけるEscapeInfo.AliasInfoプロパティの格子結合演算として自然に実装できます。

Exception Handling

例外を通じたエスケープの可能性をEscapeAnalysisがどのように扱うかも、注目に値します。単純に考えると、:the_exceptionオブジェクトに課されたエスケープ情報を、対応するtryブロックでスローされる可能性のあるすべての値へ伝播すれば十分に思えます。しかしJuliaでは、Base.current_exceptionsやrethrowなど、例外オブジェクトにアクセスする方法がほかにもあります。たとえば、次の例ではrがエスケープする可能性も、エスケープ解析で考慮する必要があります。

Analysis Usage

analyze_escapesは、SSA-IR要素のエスケープ情報を解析するためのエントリポイントです。

SROA（sroa_pass!）などの最適化は、インライン化パス（ssa_inlining_pass!）がプロシージャ間呼び出しを解決し、呼び出し先のソースを展開して簡素化したソースに適用すると、より効果的です。そのため、analyze_escapesはインライン化後のIRも解析でき、特定のメモリ関連最適化に役立つエスケープ情報を収集できます。

ただし、インライン化などの最適化パスは制御フローを変更したり、デッドコードを除去したりするため、エスケープ情報のプロシージャ間での妥当性を損なうことがあります。特に、プロシージャ間で有効なエスケープ情報を収集するには、インライン化前のIRを解析する必要があります。

このため、analyze_escapesはJuliaレベルの任意の最適化段階でIRCodeを解析できます。特に、次の2つの段階で使うことを想定しています。

  • IPO EA：インライン化前のIRを解析し、IPOで有効なエスケープ情報のキャッシュを生成する
  • Local EA：インライン化後のIRを解析し、ローカルで有効なエスケープ情報を収集する

IPO EAから得られたエスケープ情報は、ArgEscapeCacheデータ構造に変換され、グローバルにキャッシュされます。適切なget_escape_cacheコールバックをanalyze_escapesに渡すと、以前のIPO EAで導出された、インライン化されていない呼び出し先のプロシージャ間情報を利用して、エスケープ解析の精度を高められます。さらに、IPO EAのエスケープ情報を型推論に使うこともできます。たとえば、可変オブジェクトのConst/PartialStruct/MustAliasを形成することで、推論精度を高められます。

Base.Compiler.EscapeAnalysis.EscapeInfo — Type
x::EscapeInfo

エスケープ情報を表す格子で、次の性質を持ちます。

  • x.Analyzed::Bool: 格子の正式な要素ではなく、xが解析済みかどうかだけを示します

  • x.ReturnEscape::Bool: xがreturnを介して呼び出し元へエスケープする可能性を示します

  • x.ThrownEscape::BitSet: xが例外としてスローされる可能性のあるSSA文番号を記録します。

    • isempty(x.ThrownEscape): この呼び出しフレームではxは決してスローされません（最下位）
    • pc ∈ x.ThrownEscape: SSA文pcでxがスローされる可能性があります
    • -1 ∈ x.ThrownEscape: この呼び出しフレーム内の任意の箇所でxがスローされる可能性があります（最上位）

    この情報は、escape_exception!が例外による潜在的なエスケープを伝播するために使用されます。

  • x.AliasInfo::Union{Bool,IndexableFields,Unindexable}: xのフィールドまたは配列要素にエイリアスされる可能性のある値をすべて保持します。

    • x.AliasInfo === falseは、xのフィールド／要素がまだ解析されていないことを示します
    • x.AliasInfo === trueは、xのフィールド／要素を解析できないことを示します。たとえば、xの型が不明、または具象型ではないため、フィールド／要素を正確に特定できない場合です
    • x.AliasInfo::IndexableFieldsは、正確なインデックス情報とともに、オブジェクトxのフィールドにエイリアスされる可能性のある値をすべて記録します
    • x.AliasInfo::Unindexableは、正確なインデックス情報なしで、xのフィールド／要素にエイリアスされる可能性のある値をすべて記録します

  • x.Liveness::BitSet: xが生存しているべきSSA文番号を記録します。たとえば、呼び出し引数として使われる場合、呼び出し元に返される場合、または:foreigncallのために保持される場合です。

    • isempty(x.Liveness): この呼び出しフレームではxは決して使われません（最下位）
    • 0 ∈ x.Livenessには、現在解析中の呼び出しフレームの呼び出し引数であるという特別な意味もあります（そのため、呼び出し元から直ちに参照できます）。
    • pc ∈ x.Liveness: SSA文pcでxが使われる可能性があります
    • -1 ∈ x.Liveness: この呼び出しフレーム内の任意の箇所でxが使われる可能性があります（最上位）

一般的なEscapeInfoを作成するためのユーティリティコンストラクターがあります。たとえば、

  • NoEscape(): この格子の最下位（に相当する）要素で、どこにもエスケープしないことを意味します
  • AllEscape(): この格子の最上位要素で、あらゆる場所へエスケープすることを意味します

analyze_escapesは、Julia標準の型推論ルーチンと同じ方向に、これらの要素を最下位から最上位へ遷移させます。抽象状態は、最下位（に相当する）要素で初期化されます。

  • 呼び出し引数はArgEscape()として初期化されます。そのLivenessプロパティには、呼び出し引数として渡され、呼び出し元から直ちに参照できることを示す0が含まれます
  • その他の状態はNotAnalyzed()として初期化されます。これはNoEscapeよりわずかに下位にある特別な格子要素ですが、まだ解析されていないこと以外の意味は持ちません（したがって、格子の正式な要素ではありません）
