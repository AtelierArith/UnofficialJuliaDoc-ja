Dates

Dates モジュールは、日付を扱うための2つの型、Date と DateTime を提供します。それぞれ日単位とミリ秒単位の精度を表し、どちらも抽象型 TimeType のサブタイプです。型を分ける理由は単純です。より高い精度に伴う複雑さを考慮しなくてよい場合、コードの記述も、頭の中での推論も、はるかに簡単になる操作があるためです。たとえば、Date 型は1日単位の精度しか持たないため（つまり、時・分・秒を扱わないため）、タイムゾーン、夏時間、うるう秒について通常必要となる考慮は不要であり、回避できます。

Date と DateTime は、基本的に不変な Int64 ラッパーです。どちらの型も、唯一のフィールド instant は実際には UTInstant{P} 型であり、UT秒に基づいて連続的に増加するマシン上の時間軸を表します[1]。DateTime 型はタイムゾーンを認識しません（Pythonの用語では naive）。Java 8の LocalDateTime に相当します。タイムゾーン機能を追加するには、TimeZones.jl package を利用できます。これは IANA time zone database をコンパイルします。Date と DateTime はどちらも、先発グレゴリオ暦に従う ISO 8601 標準に基づいています。ISO 8601標準では、紀元前（BC/BCE）の日付の扱いに注意が必要です。一般に、紀元前の最後の日である紀元前1年12月31日の翌日は、紀元1年1月1日であり、したがって0年は存在しません。しかしISO標準では、紀元前1年を0年と定めています。そのため、0000-12-31 は 0001-01-01 の前日であり、年 -0001（そう、年はマイナス1です）は紀元前2年、年 -0002 は紀元前3年となります。

Constructors

Date 型と DateTime 型は、整数型または Period 型から、文字列の解析によって、あるいは調整関数（後述）を使って構築できます。

julia> DateTime(2013)
2013-01-01T00:00:00

julia> DateTime(2013,7)
2013-07-01T00:00:00

julia> DateTime(2013,7,1)
2013-07-01T00:00:00

julia> DateTime(2013,7,1,12)
2013-07-01T12:00:00

julia> DateTime(2013,7,1,12,30)
2013-07-01T12:30:00

julia> DateTime(2013,7,1,12,30,59)
2013-07-01T12:30:59

julia> DateTime(2013,7,1,12,30,59,1)
2013-07-01T12:30:59.001

julia> Date(2013)
2013-01-01

julia> Date(2013,7)
2013-07-01

julia> Date(2013,7,1)
2013-07-01

julia> Date(Dates.Year(2013),Dates.Month(7),Dates.Day(1))
2013-07-01

julia> Date(Dates.Month(7),Dates.Year(2013))
2013-07-01

Date または DateTime の解析には、書式文字列を使います。書式文字列では、解析対象の期間を含む「区切り付き」または「固定幅」のスロットを定義します。解析するテキストと書式文字列を Date または DateTime のコンストラクターに渡す形式は、Date("2015-01-01",dateformat"y-m-d") または DateTime("20150101",dateformat"yyyymmdd") です。

区切り付きスロットでは、連続する2つの期間の間にパーサーが期待する区切り文字を指定します。たとえば、"y-m-d" は、"2014-07-16" のような日付文字列の最初と2番目のスロットの間に、- 文字があることをパーサーに伝えます。y、m、d の各文字は、それぞれのスロットで解析する期間をパーサーに伝えます。

上記の Date(2013) などのコンストラクターと同様に、区切り付きの DateFormat では、先行する部分が指定されていれば、日付や時刻の一部を省略できます。省略された部分には通常の既定値が使われます。たとえば、Date("1981-03", dateformat"y-m-d") は 1981-03-01 を返し、Date("31/12", dateformat"d/m/y") は 0001-12-31 を返します。（既定の年は紀元1年です。）ただし、空文字列を渡すと必ず ArgumentError がスローされます。

固定幅スロットは、区切り文字を挟まず、期間を表す文字を幅の数だけ繰り返して指定します。したがって、dateformat"yyyymmdd" は、"20140716" のような日付文字列に対応します。パーサーは区切り文字がないことから固定幅スロットを判別し、ある期間文字から次の期間文字への移行を "yyyymm" として認識します。

月名をテキスト形式で解析する機能も、略称用の u と、完全な月名用の U によって利用できます。既定では英語の月名のみがサポートされるため、u は「Jan」「Feb」「Mar」などに対応し、U は「January」「February」「March」などに対応します。dayname や monthname など、名前から値へのマッピングを行う他の関数と同様に、略称と完全な月名に対応する MONTHTOVALUEABBR および MONTHTOVALUE の辞書に locale=>Dict{String,Int} マッピングを渡すことで、独自のロケールを読み込めます。

上記の例では、dateformat"" 文字列マクロを使いました。このマクロは展開時に DateFormat オブジェクトを一度だけ作成し、コードスニペットを複数回実行しても同じ DateFormat オブジェクトを使います。

julia> for i = 1:10^5
           Date("2015-01-01", dateformat"y-m-d")
       end

または、DateFormat オブジェクトを明示的に作成できます。

julia> df = DateFormat("y-m-d");

julia> dt = Date("2015-01-01",df)
2015-01-01

julia> dt2 = Date("2015-01-02",df)
2015-01-02

ブロードキャストを使う方法もあります。

julia> years = ["2015", "2016"];

julia> Date.(years, DateFormat("yyyy"))
2-element Vector{Date}:
 2015-01-01
 2016-01-01

簡便な方法として、書式文字列を直接渡すこともできます（例：Date("2015-01-01","y-m-d")）。ただし、同じ書式を繰り返し解析する場合、この形式は毎回新しい DateFormat オブジェクトを内部で作成するため、性能上のコストがかかります。

コンストラクターに加えて、Date または DateTime は、parse 関数や tryparse 関数を使って文字列から構築することもできます。これらの関数には、書式を指定する DateFormat 型の第3引数を任意で渡せます。たとえば、parse(Date, "06.23.2013", dateformat"m.d.y") のように指定するか、既定の書式を使う tryparse(DateTime, "1999-12-31T23:59:59") を使います。両関数の主な違いは、tryparse では文字列が空、または書式が無効でもエラーがスローされず、代わりに nothing が返される点です。

Julia 1.9

Julia 1.9より前は、空文字列をコンストラクターや parse に渡してもエラーにならず、適切な値として DateTime(1)、Date(1)、または Time(0) が返されていました。同様に、tryparse は nothing を返しませんでした。

解析と書式設定に関するテストおよび例一式は、stdlib/Dates/test/io.jl で確認できます。

Durations/Comparisons

Date または DateTime の内部表現は、それぞれ UTInstant{Day} と UTInstant{Millisecond} なので、2つの値の間の時間を求めるのは簡単です。Date の差は Day の数で、DateTime の差は Millisecond の数で返されます。同様に、TimeType の比較も、内部のマシン時刻（ひいては内部の Int64 値）を比較するだけです。

julia> dt = Date(2012,2,29)
2012-02-29

julia> dt2 = Date(2000,2,1)
2000-02-01

julia> dump(dt)
Date
  instant: Dates.UTInstant{Day}
    periods: Day
      value: Int64 734562

julia> dump(dt2)
Date
  instant: Dates.UTInstant{Day}
    periods: Day
      value: Int64 730151

julia> dt > dt2
true

julia> dt != dt2
true

julia> dt + dt2
ERROR: MethodError: no method matching +(::Date, ::Date)
[...]

julia> dt * dt2
ERROR: MethodError: no method matching *(::Date, ::Date)
[...]

julia> dt / dt2
ERROR: MethodError: no method matching /(::Date, ::Date)

julia> dt - dt2
4411 days

julia> dt2 - dt
-4411 days

julia> dt = DateTime(2012,2,29)
2012-02-29T00:00:00

julia> dt2 = DateTime(2000,2,1)
2000-02-01T00:00:00

julia> dt - dt2
381110400000 milliseconds

Accessor Functions

Date 型と DateTime 型は、単一の Int64 値として格納されます。そのため、アクセサー関数を使って日付の各部分やフィールドを取得できます。小文字で始まるアクセサーは、フィールドを整数として返します。

julia> t = Date(2014, 1, 31)
2014-01-31

julia> Dates.year(t)
2014

julia> Dates.month(t)
1

julia> Dates.week(t)
5

julia> Dates.day(t)
31

一方、先頭が大文字のアクセサーは、対応する Period 型で同じ値を返します。

julia> Dates.Year(t)
2014 years

julia> Dates.Day(t)
31 days

複数のフィールドを個別に取得するより、一度に取得するほうが効率的なため、複合メソッドも用意されています。

julia> Dates.yearmonth(t)
(2014, 1)

julia> Dates.monthday(t)
(1, 31)

julia> Dates.yearmonthday(t)
(2014, 1, 31)

内部の UTInstant 値や整数値を取得することもできます。

julia> dump(t)
Date
  instant: Dates.UTInstant{Day}
    periods: Day
      value: Int64 735264

julia> t.instant
Dates.UTInstant{Day}(Day(735264))

julia> Dates.value(t)
735264

Query Functions

問い合わせ関数を使うと、TimeType に関する暦情報を取得できます。たとえば、曜日に関する情報です。

julia> t = Date(2014, 1, 31)
2014-01-31

julia> Dates.dayofweek(t)
5

julia> Dates.dayname(t)
"Friday"

julia> Dates.dayofweekofmonth(t) # 5th Friday of January
5

年の中の月に関する情報です。

julia> Dates.monthname(t)
"January"

julia> Dates.daysinmonth(t)
31

また、TimeType の年や四半期に関する情報も取得できます。

julia> Dates.isleapyear(t)
false

julia> Dates.dayofyear(t)
31

julia> Dates.quarterofyear(t)
1

julia> Dates.dayofquarter(t)
31

dayname メソッドと monthname メソッドには、他の言語やロケールで曜日名または月名を返すための locale キーワード引数を任意で指定できます。略称を返す関数として、dayabbr と monthabbr もあります。まず、マッピングを LOCALES 変数に読み込みます。

julia> french_months = ["janvier", "février", "mars", "avril", "mai", "juin",
                        "juillet", "août", "septembre", "octobre", "novembre", "décembre"];

julia> french_months_abbrev = ["janv","févr","mars","avril","mai","juin",
                              "juil","août","sept","oct","nov","déc"];

julia> french_days = ["lundi","mardi","mercredi","jeudi","vendredi","samedi","dimanche"];

julia> Dates.LOCALES["french"] = Dates.DateLocale(french_months, french_months_abbrev, french_days, [""]);

その後、前述の関数を使って問い合わせを実行できます。

julia> Dates.dayname(t;locale="french")
"vendredi"

julia> Dates.monthname(t;locale="french")
"janvier"

julia> Dates.monthabbr(t;locale="french")
"janv"

曜日の略称は読み込まれていないため、関数 dayabbr を使おうとするとエラーになります。

julia> Dates.dayabbr(t;locale="french")
ERROR: BoundsError: attempt to access 1-element Vector{String} at index [5]
Stacktrace:
[...]

TimeType-Period Arithmetic

どの言語や日付フレームワークを使う場合でも、日付と期間の算術がどのように処理されるかを把握しておくのがよいでしょう。対処が必要な tricky issues がいくつかあるためです（ただし、日単位の精度を持つ型では問題はかなり少なくなります）。

Dates モジュールでは、Period 算術を行う際に、できるだけ変更を少なくするという単純な原則に従っています。この方法は 暦算術 とも呼ばれ、会話の中で同じ計算を尋ねられたときに、おそらく直感的に答える方法でもあります。なぜこれが問題になるのでしょうか。よくある例を考えてみましょう。2014年1月31日に1か月を加えると、どうなるでしょうか。JavaScriptでは March 3 となります（31日あると仮定）。PHPでは March 2 となります（30日あると仮定）。実際のところ、正解はありません。Dates モジュールでは、結果は2月28日になります。どのように求めるのでしょうか。カジノの定番スロットマシン、7-7-7を考えてみてください。

今度は、スロットの数字が7-7-7ではなく、年-月-日だと想像してください。この例では2014-01-31です。この日付に1か月を加えると、月のスロットが1つ進み、2014-02-31になります。次に、日が新しい月の最終日を超えているかを確認します。上の例のように超えていれば、日を有効な最終日（28日）まで戻します。この方法にはどのような影響があるでしょうか。元の日付 2014-02-28 + Month(1) == 2014-03-28 に、さらに1か月を加えてみてください。3月の最終日になると思いましたか。いいえ、7-7-7のスロットを思い出してください。変更するスロットはできるだけ少なくするため、まず月のスロットを1つ進めて2014-03-28とし、これは有効な日付なのでそこで終了です。一方、元の日付2014-01-31に2か月を加えると、期待どおり2014-03-31になります。この方法では、演算の順序を固定すると結合性が失われるという影響もあります（つまり、異なる順序で計算すると結果が異なります）。たとえば、次のようになります。

julia> (Date(2014,1,29)+Dates.Day(1)) + Dates.Month(1)
2014-02-28

julia> (Date(2014,1,29)+Dates.Month(1)) + Dates.Day(1)
2014-03-01

何が起きているのでしょうか。1行目では、2014年1月29日に1日を加えて2014-01-30とし、次に1か月を加えます。すると2014-02-30になりますが、これは2014-02-28に調整されます。2つ目の例では、まず1か月を加えるため、2014-02-29となり、2014-02-28に調整されます。その後、1日を加えると2014-03-01になります。この場合に役立つ設計原則の1つは、複数の Period があるとき、演算は Period の値や位置の順序ではなく、型の順序で行われることです。つまり、Year が最初に加算され、次に Month、続いて Week という順になります。そのため、次の例では結合性が保たれ、期待どおりに動作します。

julia> Date(2014,1,29) + Dates.Day(1) + Dates.Month(1)
2014-03-01

julia> Date(2014,1,29) + Dates.Month(1) + Dates.Day(1)
2014-03-01

少しややこしいでしょうか。何も知らずに Dates を使う人は、どうすればよいのでしょうか。要点は、月を扱うときに結合順序を明示的に固定すると、予想外の結果になることがあると理解しておくことです。それ以外は、すべて期待どおりに動作するはずです。幸い、UTに基づいて時間を扱う日付・期間算術で奇妙なケースは、ほぼこれだけです（夏時間やうるう秒などの「楽しさ」を避けられるためです）。

さらに、すべての期間算術オブジェクトは範囲と直接組み合わせて使えます。

julia> dr = Date(2014,1,29):Day(1):Date(2014,2,3)
Date("2014-01-29"):Day(1):Date("2014-02-03")

julia> collect(dr)
6-element Vector{Date}:
 2014-01-29
 2014-01-30
 2014-01-31
 2014-02-01
 2014-02-02
 2014-02-03

julia> dr = Date(2014,1,29):Dates.Month(1):Date(2014,07,29)
Date("2014-01-29"):Month(1):Date("2014-07-29")

julia> collect(dr)
7-element Vector{Date}:
 2014-01-29
 2014-02-28
 2014-03-29
 2014-04-29
 2014-05-29
 2014-06-29
 2014-07-29

Adjuster Functions

日付と期間の算術は便利ですが、日付に必要な計算は、固定数の期間ではなく、暦や時間的な規則に基づくことがよくあります。祝日はその典型例です。「メモリアルデー = 5月の最終月曜日」や「感謝祭 = 11月の第4木曜日」のような規則に従うものが多くあります。このような時間的な表現では、「月の最初または最後の日」「次の火曜日」「第1および第3水曜日」など、暦に基づく規則を扱います。

Dates モジュールは、時間的な規則を簡潔に表現するのに役立つ、便利な複数のメソッドを通じて adjuster API を提供します。最初のグループの adjuster メソッドは、週・月・四半期・年の最初と最後を扱います。いずれも入力として単一の TimeType を受け取り、入力を基準に、指定した期間の最初または最後へ値を返す、あるいは値を調整します。

julia> Dates.firstdayofweek(Date(2014,7,16)) # Adjusts the input to the Monday of the input's week
2014-07-14

julia> Dates.lastdayofmonth(Date(2014,7,16)) # Adjusts to the last day of the input's month
2014-07-31

julia> Dates.lastdayofquarter(Date(2014,7,16)) # Adjusts to the last day of the input's quarter
2014-09-30

次の2つの高階メソッド tonext と toprev は、第1引数に DateFunction を取り、開始点となる TimeType と組み合わせることで、時間的な規則を一般化して扱います。DateFunction は単なる関数（通常は無名関数）で、入力として単一の TimeType を受け取り、調整条件を満たす Bool または true を返します。たとえば、次のようになります。

julia> istuesday = x->Dates.dayofweek(x) == Dates.Tuesday; # Returns true if the day of the week of x is Tuesday

julia> Dates.tonext(istuesday, Date(2014,7,13)) # 2014-07-13 is a Sunday
2014-07-15

julia> Dates.tonext(Date(2014,7,13), Dates.Tuesday) # Convenience method provided for day of the week adjustments
2014-07-15

より複雑な時間的規則を表現する場合は、doブロック構文が便利です。

Period Types

期間とは、人間の視点から見た、離散的で、ときには不規則な時間の長さです。たとえば1か月は、年や月の状況によって28日、29日、30日、31日のいずれかになります。また、うるう年の場合、1年は365日または366日になります。Period 型は単純な Int64 ラッパーで、Int64 に変換可能な型、つまり Year(1) や Month(3.0) をラップして構築します。同じ型の Period 同士の算術は整数と同様に動作し、限定的な Period-Real 算術も利用できます。Dates.value を使うと、内部の整数値を取り出せます。

julia> y1 = Dates.Year(1)
1 year

julia> y2 = Dates.Year(2)
2 years

julia> y3 = Dates.Year(10)
10 years

julia> y1 + y2
3 years

julia> div(y3,y2)
5

julia> y3 - y2
8 years

julia> y3 % y2
0 years

julia> div(y3,3) # mirrors integer division
3 years

julia> Dates.value(Dates.Millisecond(10))
10

基本型の整数倍ではない期間や長さを表すには、Dates.CompoundPeriod 型を使います。複合期間は、単純な Period 型から手動で構築できます。また、canonicalize 関数を使って、期間を Dates.CompoundPeriod に分解することもできます。これは、たとえば2つの DateTime の差のような長さを、より扱いやすい表現に変換する場合に特に便利です。

julia> cp = Dates.CompoundPeriod(Day(1),Minute(1))

julia> t1 = DateTime(2018,8,8,16,58,00)
2018-08-08T16:58:00

julia> t2 = DateTime(2021,6,23,10,00,00)
2021-06-23T10:00:00

julia> canonicalize(t2-t1) # creates a CompoundPeriod
149 weeks, 6 days, 17 hours, 2 minutes

Rounding

Date と DateTime の値は、floor、ceil、または round を使って、指定した精度（例：1か月、15分）に丸めることができます。

julia> floor(Date(1985, 8, 16), Dates.Month)
1985-08-01

julia> ceil(DateTime(2013, 2, 13, 0, 31, 20), Dates.Minute(15))
2013-02-13T00:45:00

julia> round(DateTime(2016, 8, 6, 20, 15), Dates.Day)
2016-08-07T00:00:00

既定では同値の場合に偶数側へ丸める数値用の round メソッドとは異なり、TimeTyperound メソッドでは RoundNearestTiesUp 丸めモードが使われます。（「偶数」に最も近い TimeType へ同値を丸めるとはどういうことか、推測するのは難しいでしょう。）利用可能な RoundingMode の詳細は、API reference を参照してください。

丸めは通常、期待どおりに動作しますが、期待される動作が明確でないケースもいくつかあります。

Rounding Epoch

多くの場合、丸め精度（例：Dates.Second(30)）は、次に大きい期間（この場合は Dates.Minute(1)）を均等に分割できます。しかし、そうならない場合の丸め動作は混乱を招くことがあります。DateTime を最も近い10時間単位に丸めると、どのような結果になるでしょうか。

julia> round(DateTime(2016, 7, 17, 11, 55), Dates.Hour(10))
2016-07-17T12:00:00

時（12）が10で割り切れないため、混乱するかもしれません。2016-07-17T12:00:00 が選ばれたのは、0000-01-01T00:00:00 から17,676,660時間後であり、17,676,660が10で割り切れるためです。

Juliaの Date と DateTime の値はISO 8601標準に従って表現されるため、丸め計算で使う日数（およびミリ秒数）の起点、つまり「丸めエポック」には 0000-01-01T00:00:00 が選ばれています。（これは、Rata Die notation を使った Julia 内部での Date の表現とは少し異なります。ただし、ISO 8601標準のほうがエンドユーザーにとって目にする機会が多いため、混乱を避ける目的で、内部で使われる 0000-12-31T00:00:00 ではなく 0000-01-01T00:00:00 を丸めエポックに選びました。）

丸めエポックに 0000-01-01T00:00:00 を使わない唯一の例外は、週単位の丸めです。最も近い週に丸めると、必ず月曜日（ISO 8601で定められた週の初日）が返されます。そのため、週数への丸めでは、ISO 8601で定義された0000年の第1週の初日である 0000-01-03T00:00:00 を起点として使います。

期待される動作が必ずしも明らかでない関連ケースをもう1つ見てみましょう。P(2)（ここで P は Period 型）に最も近い値へ丸めると、どうなるでしょうか。いくつかのケース（具体的には P <: Dates.TimePeriod の場合）では、答えは明らかです。

julia> round(DateTime(2016, 7, 17, 8, 55, 30), Dates.Hour(2))
2016-07-17T08:00:00

julia> round(DateTime(2016, 7, 17, 8, 55, 30), Dates.Minute(2))
2016-07-17T08:56:00

これらの期間を2つずつまとめても、次に大きい単位の期間を均等に分割できるため、これは明らかに思えます。しかし、2か月の場合（1年を均等に分割できる点は同じです）は、意外な結果になることがあります。

julia> round(DateTime(2016, 7, 17, 8, 55, 30), Dates.Month(2))
2016-07-01T00:00:00

月が7（奇数）なのに、なぜ7月1日に丸められるのでしょうか。重要なのは、月は1から数える（最初の月を1とする）のに対し、時・分・秒・ミリ秒は0から数える（最初の値を0とする）ことです。

つまり、秒・分・時・年の偶数倍に DateTime を丸めると（ISO 8601仕様には0年が含まれるため）、そのフィールドの値が偶数の DateTime になります。一方、月の偶数倍に DateTime を丸めると、月フィールドの値は奇数になります。月と年には日数が一定でない場合があるため、日数の偶数倍に丸めたときに日フィールドが偶数になるかどうかは一定しません。

  • 1UT秒という概念は、実は非常に基本的なものです。一般に受け入れられている時間の考え方は大きく2つあります。地球の物理的な自転（1回転を1日とする）に基づくものと、SI秒（固定された一定の値）に基づくものです。この2つは大きく異なります。地球の自転に対して定義される「UT秒」は、日によって絶対的な長さが異なる可能性があることを考えてみてください。いずれにせよ、Date と DateTime がUT秒に基づいているのは、うるう秒などの複雑さを避けるための、簡略化でありながら誠実な前提です。この時間の基準は、正式には UT（UT1）と呼ばれます。型をUT秒に基づかせると、各分は60秒、各日は24時間となり、暦日を扱う際により自然な計算ができます。
