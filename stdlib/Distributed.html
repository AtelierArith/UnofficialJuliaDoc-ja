Distributed.addprocs — Function
addprocs(manager::ClusterManager; kwargs...) -> List of process identifiers

指定したクラスターマネージャーを介してワーカープロセスを起動します。

たとえば、パッケージ ClusterManagers.jl で実装されたカスタムクラスターマネージャーを使って、Beowulf クラスターを利用できます。

新たに起動したワーカーがマスターとの接続確立を待つ秒数は、ワーカープロセスの環境変数 JULIA_WORKER_TIMEOUT で指定できます。この設定が適用されるのは、トランスポートに TCP/IP を使用する場合のみです。

ワーカーの起動中に REPL（プログラムから起動する場合は、呼び出し元の関数）をブロックしないようにするには、addprocs を独立したタスク内で実行します。

Examples

# On busy clusters, call `addprocs` asynchronously
t = @async addprocs(...)
# Utilize workers as and when they come online
if nprocs() > 1   # Ensure at least one new worker is available
   ....   # perform distributed execution
end
# Retrieve newly launched worker IDs, or any error messages
if istaskdone(t)   # Check if `addprocs` has completed to ensure `fetch` doesn't block
    if nworkers() == N
        new_pids = fetch(t)
    else
        fetch(t)
    end
end
source
addprocs(machines; tunnel=false, sshflags=``, max_parallel=10, kwargs...) -> List of process identifiers

SSH 経由でリモートマシンにワーカープロセスを追加します。設定はキーワード引数で行います（以下を参照）。特に、exename キーワードを使うと、リモートマシン上の julia バイナリへのパスを指定できます。

machines は、[user@]host[:port] [bind_addr[:port]] 形式の文字列で指定する「マシン指定」のベクトルです。user の既定値は現在のユーザー、port の既定値は標準の SSH ポートです。[bind_addr[:port]] を指定すると、他のワーカーは指定された bind_addr と port でこのワーカーに接続します。

machines ベクトル内でタプルを使うか、(machine_spec, count) 形式を使うと、リモートホスト上で複数のプロセスを起動できます。ここで count は、指定したホスト上で起動するワーカー数です。ワーカー数に :auto を指定すると、リモートホストの CPU スレッド数と同じ数のワーカーが起動します。

例:

addprocs([
    "remote1",               # one worker on 'remote1' logging in with the current username
    "user@remote2",          # one worker on 'remote2' logging in with the 'user' username
    "user@remote3:2222",     # specifying SSH port to '2222' for 'remote3'
    ("user@remote4", 4),     # launch 4 workers on 'remote4'
    ("user@remote5", :auto), # launch as many workers as CPU threads on 'remote5'
])

キーワード引数:

  • tunnel: true の場合、マスタープロセスからワーカーへの接続に SSH トンネリングを使用します。既定値は false です。

  • multiplex: true の場合、SSH トンネリングに SSH 多重化を使用します。既定値は false です。

  • ssh: ワーカーの起動に使用する SSH クライアント実行ファイルの名前またはパスです。既定値は "ssh" です。

  • sshflags: 追加の SSH オプションを指定します。例: sshflags=`-i /home/foo/bar.pem`

  • max_parallel: ホストごとに並列接続するワーカーの最大数を指定します。既定値は 10 です。

  • shell: ワーカー上で SSH が接続するシェルの種類を指定します。

    • shell=:posix: POSIX 互換の Unix/Linux シェル（sh、ksh、bash、dash、zsh など）。既定値です。
    • shell=:csh: Unix の C シェル（csh、tcsh）。
    • shell=:wincmd: Microsoft Windows cmd.exe。

  • dir: ワーカー上の作業ディレクトリを指定します。既定値は、pwd() で取得されるホストの現在のディレクトリです。

  • enable_threaded_blas: true の場合、追加されたプロセスで BLAS が複数スレッドを使って実行されます。既定値は false です。

  • exename: julia 実行ファイルの名前です。既定値は、状況に応じて "$(Sys.BINDIR)/julia" または "$(Sys.BINDIR)/julia-debug" です。シリアライズやコード配布に失敗する可能性があるため、すべてのリモートマシンで同じ Julia バージョンを使うことを推奨します。

  • exeflags: ワーカープロセスに渡す追加のフラグです。Cmd、フラグを 1 つ含む String、またはフラグごとに 1 要素を持つ文字列のコレクションを指定できます。例: $--threads=auto project=.$、"--compile-trace=stderr"、["--threads=auto", "--compile=all"]。

  • topology: ワーカー同士の接続方法を指定します。接続されていないワーカー間でメッセージを送信すると、エラーになります。

    • topology=:all_to_all: すべてのプロセスが相互に接続されます。既定値です。
    • topology=:master_worker: ドライバープロセス、つまり pid 1 のみがワーカーに接続します。ワーカー同士は接続しません。
    • topology=:custom: クラスターマネージャーの launch メソッドが、WorkerConfig 内の ident フィールドと connect_idents フィールドを使って接続トポロジーを指定します。クラスターマネージャーの ID が ident のワーカーは、connect_idents に指定されたすべてのワーカーに接続します。

  • lazy: topology=:all_to_all と併用する場合にのみ適用されます。true の場合、ワーカー間の接続は遅延設定され、ワーカー間でリモート呼び出しが初めて行われた時点で確立されます。既定値は true です。

  • env: env=["JULIA_DEPOT_PATH"=>"/depot"] のような文字列ペアの配列を指定すると、リモートマシン上に環境変数を設定できます。既定では、ローカル環境からリモート環境へ自動的に渡されるのは JULIA_WORKER_TIMEOUT 環境変数のみです。

  • cmdline_cookie: --worker コマンドラインオプションを使って認証 Cookie を渡します。より安全な既定の方法である SSH の標準入出力経由での Cookie の受け渡しは、古い（ConPTY 導入前の）Julia または Windows バージョンを使う Windows ワーカーで停止することがあります。その場合は cmdline_cookie=true を回避策として使用できます。

Julia 1.6

キーワード引数 ssh、shell、env、cmdline_cookie は Julia 1.6 で追加されました。

環境変数:

マスタープロセスが、新たに起動したワーカーとの接続を 60.0 秒以内に確立できない場合、ワーカーは致命的な状況と判断して終了します。このタイムアウトは環境変数 JULIA_WORKER_TIMEOUT で制御できます。マスタープロセス上の JULIA_WORKER_TIMEOUT の値は、新たに起動したワーカーが接続確立を待つ秒数を指定します。

addprocs(np::Integer=Sys.CPU_THREADS; restrict=true, kwargs...) -> List of process identifiers

組み込みの LocalManager を使って、ローカルホスト上で np ワーカーを起動します。

ローカルワーカーは、メインプロセスの現在のパッケージ環境（アクティブなプロジェクト、LOAD_PATH、DEPOT_PATH）を引き継ぎます。

Warning

ワーカーは ~/.julia/config/startup.jl 起動スクリプトを実行しません。また、コマンドラインスイッチ、グローバル変数、新しいメソッド定義、読み込み済みモジュールなどのグローバル状態を、ほかの実行中プロセスと同期しないことに注意してください。

キーワード引数:

  • restrict::Bool: true（デフォルト）のバインディングを 127.0.0.1 に制限する場合に指定します。
  • dir、exename、exeflags、env、topology、lazy、enable_threaded_blas: SSHManager と同じ効果があります。詳しくは addprocs(machines::AbstractVector) のドキュメントを参照してください。

Distributed.rmprocs — Function
rmprocs(pids...; waitfor=typemax(Int))

指定したワーカーを削除します。ワーカーを追加または削除できるのはプロセス 1 だけです。

引数 waitfor は、ワーカーのシャットダウンを待つ時間を指定します。

  • 指定しない場合、rmprocs は、要求されたすべての pids が削除されるまで待機します。
  • 要求された waitfor 秒以内にすべてのワーカーを終了できない場合、ErrorException が発生します。
  • waitfor の値が 0 の場合、呼び出しは直ちに戻り、別のタスクでワーカーの削除がスケジュールされます。スケジュールされた Task オブジェクトが返されます。他の並列呼び出しを行う前に、そのタスクに対して wait を呼び出してください。

Examples

$ julia -p 5

julia> t = rmprocs(2, 3, waitfor=0)
Task (runnable) @0x0000000107c718d0

julia> wait(t)

julia> workers()
3-element Array{Int64,1}:
 4
 5
 6

Distributed.pmap — Function
pmap(f, [::AbstractWorkerPool], c...; distributed=true, batch_size=1, on_error=nothing, retry_delays=[], retry_check=nothing) -> collection

コレクション c の各要素に対して、利用可能なワーカーとタスクを使い、f を適用して変換します。

複数のコレクションを引数に指定した場合は、f を要素ごとに適用します。

f はすべてのワーカープロセスで利用可能にしておく必要があります。詳しくは Code Availability and Loading Packages を参照してください。

ワーカープールを指定しない場合は、CachingPool を介して、利用可能なすべてのワーカーが使用されます。

デフォルトでは、pmap は指定されたすべてのワーカーに計算を分散します。ローカルプロセスのみを使い、タスクに分散させるには、distributed=false を指定します。これは asyncmap を使うのと同じです。たとえば、pmap(f, c; distributed=false) は asyncmap(f,c; ntasks=()->nworkers()) と同等です。

pmap では、batch_size 引数を使って、プロセスとタスクを組み合わせることもできます。バッチサイズが 1 より大きい場合、コレクションは複数のバッチに分けて処理されます。各バッチの長さは batch_size 以下です。バッチは単一のリクエストとして空いているワーカーに送られ、そのワーカー上のローカルな asyncmap が、複数の並行タスクを使ってバッチ内の要素を処理します。

エラーが発生すると、pmap はコレクションの残りの処理を中止します。この動作を変更するには、引数 on_error でエラー処理関数を指定します。この関数は例外を単一の引数として受け取ります。エラーを再スローすると処理を中止でき、処理を続ける場合は任意の値を返します。返された値は結果に含まれ、呼び出し元に返されます。

次の 2 つの例を見てください。1 つ目は例外オブジェクトを結果に含めて返し、2 つ目は例外の代わりに 0 を返します。

julia> pmap(x->iseven(x) ? error("foo") : x, 1:4; on_error=identity)
4-element Array{Any,1}:
 1
  ErrorException("foo")
 3
  ErrorException("foo")

julia> pmap(x->iseven(x) ? error("foo") : x, 1:4; on_error=ex->0)
4-element Array{Int64,1}:
 1
 0
 3
 0

失敗した計算を再試行することで、エラーを処理することもできます。キーワード引数 retry_delays と retry_check は、それぞれキーワード引数 delays と check として retry に渡されます。バッチ処理を指定してバッチ全体が失敗した場合は、そのバッチ内のすべての項目が再試行されます。

on_error と retry_delays の両方を指定した場合、再試行の前に on_error フックが呼び出されることに注意してください。on_error が例外をスロー（または再スロー）しなければ、その要素は再試行されません。

例：エラーが発生した場合、要素に対する f の再試行を、再試行間の待ち時間なしで最大 3 回行います。

pmap(f, c; retry_delays = zeros(3))

例：例外が InexactError 型でない場合に限り、f を最大 3 回再試行し、待ち時間を指数関数的に増やします。すべての InexactError の発生箇所では、代わりに NaN を返します。

pmap(f, c; on_error = e->(isa(e, InexactError) ? NaN : rethrow()), retry_delays = ExponentialBackOff(n = 3))

Distributed.remote_do — Method
remote_do(f, id::Integer, args...; kwargs...) -> nothing

fをワーカーid上で非同期に実行します。remotecallとは異なり、計算結果は保存されず、完了を待つ方法もありません。

呼び出しが成功した場合、リモートノードでの実行要求が受け付けられたことを示します。

同じワーカーに対する連続したremotecallは、呼び出された順に直列化されますが、リモートワーカー上での実行順序は決まっていません。たとえば、remote_do(f1, 2); remotecall(f2, 2); remote_do(f3, 2)は、f1、続いてf2、f3の順に呼び出しを直列化します。しかし、ワーカー2上でf1がf3より先に実行される保証はありません。

fがスローした例外は、リモートワーカー上のstderrに出力されます。

キーワード引数がある場合は、fに渡されます。

Distributed.AbstractWorkerPool — Type
AbstractWorkerPool

WorkerPoolやCachingPoolなどのワーカープールのスーパータイプです。AbstractWorkerPoolでは、次の機能を実装する必要があります。

  • push! - 全体のプール（利用可能なワーカーと使用中のワーカー）に新しいワーカーを追加する
  • put! - ワーカーを利用可能なプールに戻す
  • take! - 利用可能なプールからワーカーを取得する（リモート関数の実行に使用）
  • wait - ワーカーが利用可能になるまでブロックする

  • channel::Channel{Int}
  • workers::Set{Int}

channelには空きワーカーのPIDが格納され、workersはこのプールに属するすべてのワーカーの集合です。

Distributed.CachingPool — Type
CachingPool(workers::Vector{Int})

AbstractWorkerPool の実装では、remote、remotecall_fetch、pmap（および関数をリモートで実行するその他のリモート呼び出し）において、シリアライズ／デシリアライズした関数をワーカーノード上にキャッシュすると効果があります。特に、クロージャ（大量のデータをキャプチャする場合があります）で有効です。

リモートキャッシュは、返された CachingPool オブジェクトの存続期間中保持されます。キャッシュをそれより早くクリアするには、clear!(pool) を使用します。

グローバル変数については、クロージャにキャプチャされるのはバインディングのみで、データ自体はキャプチャされません。グローバルデータをキャプチャするには、let ブロックを使用できます。

Examples

const foo = rand(10^8);
wp = CachingPool(workers())
let foo = foo
    pmap(i -> sum(foo) + i, wp, 1:100);
end

上記の方法では、foo は各ワーカーに一度だけ転送されます。

Distributed.@distributed — Macro
@distributed

分散メモリ上で並列に実行する for ループは、次の形式です。

@distributed [reducer] for var = range
    body
end

指定した範囲は分割され、すべてのワーカーでローカルに実行されます。オプションのリデューサー関数を指定した場合、@distributed は各ワーカーでローカルなリダクションを行い、呼び出し元のプロセスで最終的なリダクションを行います。

リデューサー関数を指定しない場合、@distributed は非同期に実行されます。つまり、利用可能なすべてのワーカーで独立したタスクを起動し、完了を待たずに直ちに戻ります。完了を待つには、次のように呼び出しの前に @sync を付けます。

@sync @distributed for var = range
    body
end
source
Distributed.@everywhere — Macro
@everywhere [procs()] expr

Main の式を、すべての procs 上で実行します。いずれかのプロセスで発生したエラーは CompositeException にまとめられ、スローされます。たとえば、次のようにします。

@everywhere bar = 1

これにより、現在のすべてのプロセスで Main.bar が定義されます。後から追加されたプロセス（たとえば addprocs()）では、この式は定義されません。

@spawnat とは異なり、@everywhere はローカル変数をキャプチャしません。代わりに、補間を使ってローカル変数をブロードキャストできます。

foo = 1
@everywhere bar = $foo

省略可能な引数 procs を指定すると、式を実行するプロセスを全プロセスの一部に限定できます。

remotecall_eval(Main, procs, expr) の呼び出しと同様ですが、次の2つの機能が追加されています。

  • using 文と import 文は、パッケージが事前コンパイルされるよう、まず呼び出し元のプロセスで実行されます。
  • include が使用する現在のソースファイルのパスが、他のプロセスにも引き継がれます。

Distributed.remoteref_id — Function
remoteref_id(r::AbstractRemoteRef) -> RRID

FutureとRemoteChannelは、次のフィールドで識別されます。

  • where - 参照先のオブジェクトまたはストレージが実際に存在するノードを指します。
  • whence - リモート参照が作成された元のノードを指します。これは、参照先のオブジェクトが実際に存在するノードとは異なる点に注意してください。たとえば、マスタープロセスからRemoteChannel(2)を呼び出すと、whereの値は2、whenceの値は1になります。
  • idは、whenceで指定されたワーカーから作成されたすべての参照の中で一意です。

whenceとidを組み合わせると、すべてのワーカーにわたって参照を一意に識別できます。

remoteref_idは低レベルAPIで、リモート参照のwhence値とid値をラップするRRIDオブジェクトを返します。

Cluster Manager Interface

このインターフェースを使うと、さまざまなクラスタ環境で Julia ワーカーを起動し、管理できます。Base には 2 種類のマネージャーがあります。LocalManager は同じホスト上でワーカーを追加起動し、SSHManager は ssh 経由でリモートホスト上にワーカーを起動します。プロセス間の接続とメッセージの転送には TCP/IP ソケットを使用します。クラスタマネージャーによっては、別のトランスポートを提供することもできます。

Distributed.ClusterManager — Type
ClusterManager

ワーカープロセスをクラスターとして制御するクラスターマネージャーのスーパータイプです。クラスターマネージャーは、ワーカーの追加・削除方法や、ワーカーとの通信方法を実装します。SSHManager と LocalManager は、この型のサブタイプです。

source
Distributed.WorkerConfig — Type
WorkerConfig

ClusterManagerがクラスターに追加するワーカーを制御するために使用する型です。一部のフィールドは、すべてのクラスター管理ツールがホストにアクセスする際に使用します。

  • io – ワーカーへの接続（IOまたはNothingのサブタイプ）
  • host – ホストアドレス（StringまたはNothing）
  • port – ワーカーへの接続に使用するホスト上のポート（IntまたはNothing）

一部のフィールドは、初期化済みのホストにワーカーを追加する際に、クラスター管理ツールが使用します。

  • count – ホスト上で起動するワーカーの数
  • exename – ホスト上のJulia実行ファイルへのパス。デフォルトは"$(Sys.BINDIR)/julia"または"$(Sys.BINDIR)/julia-debug"
  • exeflags – リモートでJuliaを起動する際に使用するフラグ

userdataフィールドは、外部管理ツールが各ワーカーの情報を格納するために使用します。

一部のフィールドは、SSHManagerなどの管理ツールが使用します。

  • tunnel – true（トンネリングを使用）、false（トンネリングを使用しない）、またはnothing（管理ツールのデフォルトを使用）
  • multiplex – true（トンネリングにSSH多重化を使用）またはfalse
  • forward – sshの-Lオプションに使用する転送オプション
  • bind_addr – リモートホストでバインドするアドレス
  • sshflags – SSH接続の確立に使用するフラグ
  • max_parallel – ホスト上で並列に接続するワーカーの最大数

一部のフィールドは、LocalManagerとSSHManagerの両方が使用します。

  • connect_at – ワーカー間接続か、ドライバーからワーカーへの接続かを判定します
  • process – 接続対象のプロセス（通常、管理ツールがaddprocs中に割り当てます）
  • ospid – ホストOS上のプロセスID。ワーカープロセスの割り込みに使用します
  • environ – Local/SSH管理ツールが一時情報を格納するためのプライベート辞書
  • ident – ClusterManagerで識別されるワーカー
  • connect_idents – カスタムトポロジーを使用する場合に、ワーカーが接続する必要のあるワーカーIDのリスト
  • enable_threaded_blas – true、false、またはnothing。ワーカーでスレッド化BLASを使用するかどうかを指定します
