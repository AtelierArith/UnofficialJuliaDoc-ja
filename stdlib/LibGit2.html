LibGit2

LibGit2 モジュールは、libgit2（Git バージョン管理システムの中核機能を実装する、移植性の高い C ライブラリ）へのバインディングを提供します。これらのバインディングは現在、Julia のパッケージマネージャーを支えるために使われています。将来的には、このモジュールは独立したパッケージに移される予定です。

Functionality

このドキュメントの一部では、libgit2 API に関する予備知識があることを前提としています。ここで言及しているオブジェクトやメソッドについて詳しくは、上流の libgit2 API reference を参照してください。

LibGit2.Buffer — Type
LibGit2.Buffer

libgit2 からデータをエクスポートするためのデータバッファです。git_buf 構造体に対応します。

LibGit2 からデータを取得する際の一般的な使用例は、次のとおりです。

buf_ref = Ref(Buffer())
@check ccall(..., (Ptr{Buffer},), buf_ref)
# operation on buf_ref
free(buf_ref)

特に、Ref オブジェクトに対して、その後 LibGit2.free を呼び出す必要がある点に注意してください。

LibGit2.CheckoutOptions — Type
LibGit2.CheckoutOptions

git_checkout_options 構造体に対応します。

各フィールドの意味は次のとおりです。

  • version: 後で変更される場合に備えた、使用中の構造体のバージョン。現時点では常に 1 です。
  • checkout_strategy: 競合の処理方法と、チェックアウトを強制するか、欠落ファイルを再作成するかを指定します。
  • disable_filters: 0 以外の場合、CLRF（ファイルの改行コードを UNIX と DOS の間で変換するフィルターなど）を適用しません。
  • dir_mode: チェックアウトに関係するディレクトリの読み取り／書き込み／アクセスモード。デフォルトは 0755 です。
  • file_mode: チェックアウトに関係するファイルの読み取り／書き込み／アクセスモード。デフォルトは、blob に応じて 0755 または 0644 です。
  • file_open_flags: チェックアウト中にファイルを開く際に使用するビットフラグ。
  • notify_flags: ユーザーに通知する競合の種類を指定するフラグ。
  • notify_cb: チェックアウトで競合が発生した場合にユーザーへ通知する、任意のコールバック関数。この関数が 0 以外の値を返すと、チェックアウトはキャンセルされます。
  • notify_payload: 通知コールバック関数に渡すペイロード。
  • progress_cb: チェックアウトの進行状況を表示する、任意のコールバック関数。
  • progress_payload: 進行状況コールバックに渡すペイロード。
  • paths: 空でない場合、チェックアウト中に検索するパスを指定します。空の場合、リポジトリ内のすべてのファイルがチェックアウト対象になります。
  • baseline: workdir の想定内容。GitTree へのポインター（またはそのポインター）に格納されます。デフォルトは HEAD におけるツリーの状態です。
  • baseline_index: workdir の想定内容。GitIndex へのポインター（またはそのポインター）に格納されます。デフォルトは HEAD におけるインデックスの状態です。
  • target_directory: 空でない場合、workdir ではなく、このディレクトリにチェックアウトします。
  • ancestor_label: 競合が発生した場合、共通祖先側の名前。
  • our_label: 競合が発生した場合、「ours」側の名前。
  • their_label: 競合が発生した場合、「theirs」側の名前。
  • perfdata_cb: パフォーマンスデータを表示する、任意のコールバック関数。
  • perfdata_payload: パフォーマンスコールバックに渡すペイロード。

LibGit2.CloneOptions — Type
LibGit2.CloneOptions

git_clone_options 構造体に一致します。

各フィールドの意味は次のとおりです。

  • version: 後で変更される場合に備えた、使用中の構造体のバージョン。現時点では常に 1 です。
  • checkout_opts: クローンの一環としてリモートをチェックアウトする際のオプション。
  • fetch_opts: クローンの一環として、チェックアウト前にリモートをフェッチする際のオプション。
  • bare: 0 の場合、リモートリポジトリ全体をクローンします。ゼロ以外の場合はベアクローンを実行します。ベアクローンでは、リポジトリ内にソースファイルのローカルコピーがなく、gitdir と workdir は同じになります。
  • localclone: ローカルのオブジェクトデータベースをクローンするか、フェッチを行うかを指定するフラグ。デフォルトでは git に判断を任せます。ローカルクローンでは git 対応のトランスポートを使用しませんが、file:// で始まる URL では使用します。
  • checkout_branch: チェックアウトするブランチ名。空文字列の場合、リモートのデフォルトブランチをチェックアウトします。
  • repository_cb: クローン先となる 新しい リポジトリを作成するために使用する、任意のコールバック。
  • repository_cb_payload: リポジトリコールバックに渡すペイロード。
  • remote_cb: クローン元となる GitRemote を作成するために、クローンの実行前に使用する任意のコールバック。
  • remote_cb_payload: リモートコールバックに渡すペイロード。

LibGit2.DescribeOptions — Type
LibGit2.DescribeOptions

git_describe_options 構造体に一致します。

各フィールドの意味は次のとおりです。

  • version: 後で構造体のバージョンが変更された場合に備えて、使用中の構造体のバージョンを示します。現時点では、常に 1 です。
  • max_candidates_tags: コミットを説明するタグを探すため、refs/tags 内の最新のタグをこの数だけ調べます。デフォルトは 10 です（つまり、コミットを説明するタグがあるかどうかを確認するため、最新の 10 個のタグを調べます）。
  • describe_strategy: refs/tags（git-describe --tags と同等）のすべてのエントリを対象にするか、refs/（git-describe --all と同等）のすべてのエントリを対象にするかを指定します。デフォルトでは、注釈付きタグのみが表示されます。Consts.DESCRIBE_TAGS を渡すと、注釈付きかどうかを問わず、すべてのタグが対象になります。Consts.DESCRIBE_ALL を渡すと、refs/ 内のすべての参照が対象になります。
  • pattern: pattern に一致するタグのみを対象にします。glob 展開に対応しています。
  • only_follow_first_parent: 一致する参照から説明対象のオブジェクトまでの距離を求める際、最初の親からの距離のみを対象にします。
  • show_commit_oid_as_fallback: コミットを説明する一致する参照が見つからない場合、エラーをスローせず、コミットの GitHash を表示します（これがデフォルトの動作です）。

LibGit2.DiffDelta — Type
LibGit2.DiffDelta

1つのエントリに対する変更の説明。git_diff_delta 構造体に対応します。

各フィールドの意味は次のとおりです。

  • status: ファイルが追加・変更・削除されたかを示す、Consts.DELTA_STATUS のいずれか。
  • flags: 差分と両側のオブジェクトに関するフラグ。ファイルをバイナリとして扱うかテキストとして扱うか、差分の各側にファイルが存在するか、オブジェクト ID が正しいと確認されているかを判定します。
  • similarity: ファイルの名前が変更されたか、コピーされたかを示します。
  • nfiles: 差分に含まれるファイル数（たとえば、サブモジュールのコミット ID に対して差分を実行した場合、複数のファイルが含まれることがあります）。
  • old_file: 変更前のファイルに関する情報を含む DiffFile。
  • new_file: 変更後のファイルに関する情報を含む DiffFile。

LibGit2.DiffFile — Type
LibGit2.DiffFile

デルタの片側の説明です。git_diff_file 構造体に対応します。

各フィールドの意味は次のとおりです。

  • id: diff 内の項目の GitHash です。diff のこの側で項目が空の場合（たとえば、ファイルの削除を表す diff の場合）、値は GitHash(0) になります。
  • path: リポジトリの作業ディレクトリを基準とした、項目への NULL 終端のパスです。
  • size: 項目のサイズ（バイト単位）です。
  • flags: git_diff_flag_t フラグを組み合わせた値です。この整数の i ビット目が、i フラグ目を設定します。
  • mode: 項目の stat モードです。
  • id_abbrev: LibGit2 のバージョンが 0.25.0 以上の場合にのみ存在します。string を使って変換したときの id フィールドの長さです。通常は OID_HEXSZ（40）と同じです。

LibGit2.DiffOptionsStruct — Type
LibGit2.DiffOptionsStruct

git_diff_options 構造体に一致します。

各フィールドの意味は次のとおりです。

  • version: 後で変更される場合に備えて指定する、使用中の構造体のバージョン。現時点では、常に 1 です。
  • flags: diff に表示するファイルを制御するフラグ。デフォルトは DIFF_NORMAL です。
  • ignore_submodules: サブモジュール内のファイルを調べるかどうか。デフォルトは SUBMODULE_IGNORE_UNSPECIFIED です。この場合、サブモジュールの設定によって diff に表示するかどうかが決まります。
  • pathspec: diff に含めるファイルのパス。デフォルトでは、リポジトリ内のすべてのファイルが対象になります。
  • notify_cb: ファイル差分が追加されるたびに、diff の変更をユーザーに通知する任意のコールバック。
  • progress_cb: diff の進行状況を表示する任意のコールバック。libgit2 のバージョンが 0.24.0 以降の場合にのみ有効です。
  • payload: notify_cb および progress_cb に渡すペイロード。
  • context_lines: ハンクの境界を定義するために使用する、変更されていない行数。ハンクの前後にコンテキストとして表示される行数もこれと同じです。デフォルトは 3 です。
  • interhunk_lines: 別々のハンク間に許容される、変更されていない行の最大数。この数を超えると、ハンクは結合されます。デフォルトは 0 です。
  • id_abbrev: 表示する GitHash の省略形の長さを設定します。デフォルトは 7 です。
  • max_size: blob の最大ファイルサイズ。このサイズを超えると、バイナリ blob として扱われます。デフォルトは 512 MB です。
  • old_prefix: diff の片側で古いファイルを配置する仮想ファイルディレクトリ。デフォルトは "a" です。
  • new_prefix: diff の片側で新しいファイルを配置する仮想ファイルディレクトリ。デフォルトは "b" です。

LibGit2.FetchHead — Type
LibGit2.FetchHead

フェッチ時の HEAD に関する情報を保持します。フェッチ元のブランチ名と URL、HEAD の oid、およびフェッチした HEAD がローカルにマージ済みかどうかが含まれます。

各フィールドの内容は次のとおりです。

  • name: フェッチヘッドのローカル参照データベース上の名前。たとえば、"refs/heads/master"。
  • url: フェッチヘッドの URL。
  • oid: フェッチヘッドの先端の GitHash。
  • ismerge: リモートの変更がローカルコピーにまだマージされていないかどうかを示すブール値フラグ。true の場合、ローカルコピーはリモートのフェッチヘッドと同期しています。

LibGit2.FetchOptions

git_fetch_options構造体に一致します。

LibGit2.GitRevWalker — Type
GitRevWalker(repo::GitRepo)

GitRevWalker は、Git リポジトリ repo の リビジョン（つまりコミット）を順にたどります。これはリポジトリ内のコミットを集めたもので、反復処理に対応し、LibGit2.map および LibGit2.count を呼び出せます（たとえば、LibGit2.count を使って、特定の作者がリポジトリ内で作成したコミットの割合を求められます）。

cnt = LibGit2.with(LibGit2.GitRevWalker(repo)) do walker
    LibGit2.count((oid,repo)->(oid == commit_oid1), walker, oid=commit_oid1, by=LibGit2.Consts.SORT_TIME)
end

ここでは、LibGit2.count によって、指定した GitHash を持つ、ウォーク上のコミット数を求めます。GitHash はコミットごとに一意なので、cnt は 1 になります。

LibGit2.MergeOptions — Type
LibGit2.MergeOptions

git_merge_options 構造体に対応します。

各フィールドの意味は次のとおりです。

  • version: 後で構造体の仕様が変更された場合に備えた、使用中の構造体のバージョン。現時点では常に 1 です。

  • flags: マージの動作を指定するフラグを表す enum。git_merge_flag_t で定義されています。対応する Julia の列挙型は GIT_MERGE で、次の値を取ります。

    • MERGE_FIND_RENAMES: 共通の祖先からマージの「ours」側または「theirs」側にかけて、ファイル名が変更されたかどうかを検出します。ファイル名が変更された場合でもマージできるようにします。
    • MERGE_FAIL_ON_CONFLICT: 競合が見つかった時点で、解決を試みずに直ちに終了します。
    • MERGE_SKIP_REUC: マージ後のインデックスに REUC 拡張を書き込みません。
    • MERGE_NO_RECURSIVE: マージ対象のコミットに複数のマージベースがある場合、ベースを再帰的にマージせず、最初のものを使用します。

  • rename_threshold: 2つのファイルを同一ファイルの改名とみなすために必要な類似度。類似度をパーセンテージで指定する整数です。既定値は 50 です。

  • target_limit: 改名を検出するために比較するファイルの最大数。既定値は 200 です。

  • metric: 改名検出で2つのファイルの類似度を判定するために使用する、任意のカスタム関数。

  • recursion_limit: マージ用の新しい仮想マージベースを構築するために、共通祖先のマージを試みる回数の上限。既定では上限はありません。このフィールドは、libgit2 のバージョンが 0.24.0 より新しい場合にのみ存在します。

  • default_driver: 両方の側で変更がある場合に使用するマージドライバー。このフィールドは、libgit2 のバージョンが 0.25.0 より新しい場合にのみ存在します。

  • file_favor: text ドライバーで、ファイル内容の競合をどのように処理するか。

    • MERGE_FILE_FAVOR_NORMAL: マージの両側で同じセクションが変更されている場合、インデックスに競合の情報を記録します。git checkout はこの情報を使ってマージファイルを作成し、ユーザーはそのファイルを参照して競合を解決できます。これが既定の動作です。
    • MERGE_FILE_FAVOR_OURS: マージの両側で同じセクションが変更されている場合、インデックスではマージの「ours」側のバージョンを使用します。
    • MERGE_FILE_FAVOR_THEIRS: マージの両側で同じセクションが変更されている場合、インデックスではマージの「theirs」側のバージョンを使用します。
    • MERGE_FILE_FAVOR_UNION: マージの両側で同じセクションが変更されている場合、両側にある重複しない各行を、インデックスに格納するファイルに含めます。

  • file_flags: ファイルをマージする際の指針。

プロキシ経由で接続するためのオプションです。

LibGit2.add! — Function
add!(repo::GitRepo, files::AbstractString...; flags::Cuint = Consts.INDEX_ADD_DEFAULT)
add!(idx::GitIndex, files::AbstractString...; flags::Cuint = Consts.INDEX_ADD_DEFAULT)

filesで指定されたパスのファイルをすべて、idx（またはrepoのインデックス）に追加します。ファイルがすでに存在する場合は、インデックスのエントリが更新されます。まだ存在しない場合は、新たにインデックスに追加されます。filesには、展開されるグロブパターンを指定できます。一致するファイルはすべて追加されます（ただし、INDEX_ADD_DISABLE_PATHSPEC_MATCHが設定されている場合を除きます。下記参照）。ファイルが（.gitignoreまたは設定ファイルで）無視対象になっている場合、インデックスですでに追跡されているファイルを更新する場合を除き、追加されません。キーワード引数flagsは、無視対象ファイルの扱いを制御するビットフラグの集合です。

clone(repo_url::AbstractString, repo_path::AbstractString; kwargs...)

repo_url にあるリモートリポジトリを、ローカルファイルシステム上の repo_path にクローンします。

キーワード引数は次のとおりです。

  • branch::AbstractString="": リモートのどのブランチをクローンするかを指定します。指定しない場合は、リポジトリのデフォルトブランチ（通常は master）が使われます。
  • isbare::Bool=false: true の場合、リモートをベアリポジトリとしてクローンします。この場合、repo_path 自体が repo_path/.git ではなく Git ディレクトリになります。そのため、作業ツリーはチェックアウトできません。Git CLI の引数 --bare に相当します。
  • remote_cb::Ptr{Cvoid}=C_NULL: クローンの前にリモートを作成するために使うコールバックです。C_NULL（デフォルト）の場合、リモートの作成は試みず、すでに存在するものとして扱います。
  • depth::Integer=0: 指定したコミット数まで履歴を切り詰めたシャロークローンを作成します。0 は完全なクローン（デフォルト）を指定します。シャロークローンから不足しているデータをすべて取得するには、Consts.FETCH_DEPTH_UNSHALLOW を使います。注: 執筆時点では、シャロークローンはネットワークプロトコル（http、https、git、ssh）でのみサポートされており、ローカルファイルシステムのパスではサポートされていません。（https://github.com/libgit2/libgit2/issues/6634)
  • credentials::Creds=nothing: プライベートリポジトリの認証に使う認証情報や設定を指定します。
  • callbacks::Callbacks=Callbacks(): ユーザーが指定するコールバックとペイロードです。

git clone [-b <branch>] [--bare] [--depth <depth>] <repo_url> <repo_path> と同等です。

Examples

repo_url = "https://github.com/JuliaLang/Example.jl"
repo1 = LibGit2.clone(repo_url, "test_path")
repo2 = LibGit2.clone(repo_url, "test_path", isbare=true)
julia_url = "https://github.com/JuliaLang/julia"
julia_repo = LibGit2.clone(julia_url, "julia_path", branch="release-0.6")
# Shallow clone with only the most recent commit
shallow_repo = LibGit2.clone(repo_url, "shallow_path", depth=1)

LibGit2.count(f::Function, walker::GitRevWalker; oid::GitHash=GitHash(), by::Cint=Consts.SORT_NONE, rev::Bool=false)

end

LibGit2.countは、特定のGitHash commit_oid1を持つコミットのうち、そのコミットからたどり始めて時系列の順に進んだときに見つかる数を返します。GitHashはコミットごとに一意であるため、cntは1になります。

LibGit2.merge_analysis — Function
merge_analysis(repo::GitRepo, anns::Vector{GitAnnotated}) -> analysis, preference

注釈付きブランチの先端が指す anns を解析し、どのような条件でマージできるかを判定します。たとえば、anns[1] が単に ann[2] の祖先である場合、merge_analysis は早送りマージが可能であると報告します。

出力は analysis と preference の2つです。analysis には、次のような値があります。 * MERGE_ANALYSIS_NONE: anns の要素をマージできません。 * MERGE_ANALYSIS_NORMAL: HEAD と、ユーザーがマージしようとしているコミットが、すべて共通の祖先から分岐している場合の通常のマージです。この場合、変更を解決する必要があり、競合が発生することもあります。 * MERGE_ANALYSIS_UP_TO_DATE: ユーザーがマージしようとしている入力コミットはすべて HEAD から到達可能なため、マージは不要です。 * MERGE_ANALYSIS_FASTFORWARD: 入力コミットは HEAD の子孫であるため、マージは不要です。代わりに、ユーザーは入力コミットをチェックアウトできます。 * MERGE_ANALYSIS_UNBORN: リポジトリの HEAD が存在しないコミットを参照しています。マージはできませんが、入力コミットをチェックアウトできる場合があります。preference にも、次のような値があります。 * MERGE_PREFERENCE_NONE: ユーザーに希望はありません。 * MERGE_PREFERENCE_NO_FASTFORWARD: 早送りマージを一切許可しません。 * MERGE_PREFERENCE_FASTFORWARD_ONLY: 早送りマージのみを許可し、競合が発生する可能性のある他の種類のマージは許可しません。preference は、リポジトリまたはグローバルの Git 設定で制御できます。

ieのステージ番号を取得します。ステージ番号0は作業ツリーの現在の状態を表しますが、マージコンフリクトが発生した場合は、ほかの番号が使われることがあります。その場合、IndexEntryにある各ステージ番号は、ファイルの現在の状態がコンフリクトのどちら側（または両側）に属するかを示します。ステージ0はマージを試みる前の状態、ステージ1はローカルで行われた変更を表します。ステージ2以降は、ほかのブランチからの変更を表します（たとえば、複数ブランチをマージする「オクトパス」マージでは、ステージ2、3、4が使われることがあります）。

LibGit2.treewalk — Function
treewalk(f, tree::GitTree, post::Bool=false)

treeとその部分木の各エントリを、ポストオーダーまたはプレオーダーで走査します。プレオーダーでは、ルートから始め、最も左の部分木を走査します（その部分木の最も左の部分木を再帰的にたどりながら下へ進みます）。その後、部分木を右へ順にたどります。ポストオーダーでは、最も左の部分木の最下部から始めて上へたどり、次に右隣の部分木を同様に最下部から走査し、最後にツリーのルートを訪問します。

関数パラメーターfは、次のシグネチャを持つ必要があります。

(String, GitTreeEntry) -> Cint

fが負の値を返すと、ツリーの走査を停止します。正の値を返すと、postがfalseの場合、そのエントリはスキップされます。

LibGit2.Consts.GIT_CONFIG — Type

設定ファイルの優先度。

これらの優先度は、Git が設定項目を検索する際の自然な優先順位（高い順）に対応しています。

  • CONFIG_LEVEL_DEFAULT - グローバル、XDG、システムの各設定ファイルが存在する場合は、それらを開きます。
  • CONFIG_LEVEL_PROGRAMDATA - Windows では、portable git との互換性のため、システム全体に適用されます。
  • CONFIG_LEVEL_SYSTEM - システム全体の設定ファイル。Linux システムでは /etc/gitconfig
  • CONFIG_LEVEL_XDG - XDG 互換の設定ファイル。通常は ~/.config/git/config
  • CONFIG_LEVEL_GLOBAL - ユーザー固有の設定ファイル（グローバル設定ファイルとも呼ばれます）。通常は ~/.gitconfig
  • CONFIG_LEVEL_LOCAL - リポジトリ固有の設定ファイル。ベアでないリポジトリでは $WORK_DIR/.git/config
  • CONFIG_LEVEL_WORKTREE - ワークツリー固有の設定ファイル。$GIT_DIR/config.worktree
  • CONFIG_LEVEL_APP - アプリケーション固有の設定ファイル。アプリケーションが自由に定義します。
  • CONFIG_HIGHEST_LEVEL - 利用可能な設定ファイルのうち最も高い優先度を表します（つまり、実際に読み込まれる設定ファイルの中で最も具体的なもの）。
