Profiling

CPU Profiling

There are two main approaches to CPU profiling julia code:

Via @profile

Where profiling is enabled for a given call via the @profile macro.

julia> using Profile

julia> @profile foo()

julia> Profile.print()
Overhead ╎ [+additional indent] Count File:Line; Function
=========================================================
    ╎147  @Base/client.jl:506; _start()
        ╎ 147  @Base/client.jl:318; exec_options(opts::Base.JLOptions)
...

Triggered During Execution

Tasks that are already running can also be profiled for a fixed time period at any user-triggered time.

To trigger the profiling:

  • MacOS & FreeBSD (BSD-based platforms): Use ctrl-t or pass a SIGINFO signal to the julia process i.e. % kill -INFO $julia_pid
  • Linux: Pass a SIGUSR1 signal to the julia process i.e. % kill -USR1 $julia_pid
  • Windows: Not currently supported.

First, a single stack trace at the instant that the signal was thrown is shown, then a 1 second profile is collected, followed by the profile report at the next yield point, which may be at task completion for code without yield points e.g. tight loops.

Optionally set environment variable JULIA_PROFILE_PEEK_HEAP_SNAPSHOT to 1 to also automatically collect a heap snapshot.

julia> foo()
##== the user sends a trigger while foo is running ==##
load: 2.53  cmd: julia 88903 running 6.16u 0.97s

======================================================================================
Information request received. A stacktrace will print followed by a 1.0 second profile
======================================================================================

signal (29): Information request: 29
__psynch_cvwait at /usr/lib/system/libsystem_kernel.dylib (unknown line)
_pthread_cond_wait at /usr/lib/system/libsystem_pthread.dylib (unknown line)
...

======================================================================
Profile collected. A report will print if the Profile module is loaded
======================================================================

Overhead ╎ [+additional indent] Count File:Line; Function
=========================================================
Thread 1 Task 0x000000011687c010 Total snapshots: 572. Utilization: 100%
   ╎147 @Base/client.jl:506; _start()
       ╎ 147 @Base/client.jl:318; exec_options(opts::Base.JLOptions)
...

Thread 2 Task 0x0000000116960010 Total snapshots: 572. Utilization: 0%
   ╎572 @Base/task.jl:587; task_done_hook(t::Task)
      ╎ 572 @Base/task.jl:879; wait()
...

Customization

The duration of the profiling can be adjusted via Profile.set_peek_duration

The profile report is broken down by thread and task. Pass a no-arg function to Profile.peek_report[] to override this. i.e. Profile.peek_report[] = () -> Profile.print() to remove any grouping. This could also be overridden by an external profile data consumer.

Profile.print — Function
print([io::IO = stdout,] [data::Vector = fetch()], [lidict::Union{LineInfoDict, LineInfoFlatDict} = getdict(data)]; kwargs...)
print(path::String, [cols::Int = 1000], [data::Vector = fetch()], [lidict::Union{LineInfoDict, LineInfoFlatDict} = getdict(data)]; kwargs...)

プロファイリング結果をio（デフォルトではstdout）に出力します。dataベクトルを指定しない場合は、蓄積されたバックトレースの内部バッファが使用されます。対応するターミナルではパスがクリック可能なリンクになり、JULIA_EDITOR向けに行番号付きで表示されます。エディタが設定されていない場合は、ファイルへのリンクのみが表示されます。

キーワード引数には、次のいずれかを任意に組み合わせて指定できます。

  • format – バックトレースを、ツリー構造を示すインデント付き（デフォルトの:tree）で表示するか、インデントなし（:flat）で表示するかを指定します。
  • C – trueの場合、CおよびFortranコードのバックトレースも表示します（通常は除外されます）。
  • combine – true（デフォルト）の場合、同じコード行に対応する命令ポインタをまとめます。
  • maxdepth – :tree形式で、maxdepthを超える深さを制限します。
  • sortedby – :flat形式での並び順を指定します。:filefuncline（デフォルト）はソース行順、:countは収集されたサンプル数順、:overheadは各関数単独で発生したサンプル数順に並べます。
  • groupby – タスクやスレッドごとにグループ化するか、グループ化しないかを指定します。選択肢は:none（デフォルト）、:thread、:task、[:thread, :task]、[:task, :thread]です。最後の2つでは、入れ子状にグループ化されます。
  • noisefloor – サンプルのヒューリスティックなノイズフロアを超えるフレームを制限します（:tree形式にのみ適用）。試す値としては2.0が推奨されます（デフォルトは0）。このパラメータは、n <= noisefloor * √Nとなるサンプルを非表示にします。ここで、nはこの行のサンプル数、Nは呼び出し先のサンプル数です。
  • mincount – mincount回以上出現する行だけに出力を制限します。
  • recur – :tree形式での再帰処理を指定します。:off（デフォルト）は通常どおりツリーを出力します。:flatは再帰を（ip単位で）圧縮し、自己再帰をイテレータに変換した場合のおおよその効果を示します。:flatcも同様ですが、Cフレームの折りたたみも行います（jl_applyの周辺では予期しない動作をする場合があります）。
  • threads::Union{Int,AbstractVector{Int}} – レポートに含めるスナップショットのスレッドを指定します。サンプルを収集するスレッドを制御するものではない点に注意してください（サンプルは別のマシンで収集されている場合もあります）。
  • tasks::Union{Int,AbstractVector{Int}} – レポートに含めるスナップショットのタスクを指定します。サンプルを収集するタスクを制御するものではない点に注意してください。
Julia 1.8

groupby、threads、tasksの各キーワード引数は、Julia 1.8で導入されました。

Note

Windowsでのプロファイリングはメインスレッドに限られます。他のスレッドはサンプリングされていないため、レポートには表示されません。

Profile.init — Function
init(; n::Integer, delay::Real)

バックトレース間の間隔（秒単位）をdelayで、スレッドごとに保存できる命令ポインターの数をnで設定します。各命令ポインターはコードの1行に対応し、バックトレースは通常、多数の命令ポインターで構成されます。バックトレースごとに、命令ポインター用の領域のうち6つはメタデータと2つのNULL終端マーカーの保存に使われることに注意してください。引数なしでこの関数を呼び出すと現在の設定を取得できます。また、キーワードを使うか、(n, delay)の順に指定することで、それぞれ個別に設定できます。

source
Profile.fetch — Function
fetch(;include_meta = true) -> data

プロファイルのバックトレースバッファのコピーを返します。dataの値は、JITコンパイルで使用される正確なメモリアドレスに依存するため、現在のセッション中にこのマシン上でのみ意味を持つことに注意してください。この関数は主に内部向けです。ほとんどのユーザーには、retrieveのほうが適している場合があります。デフォルトでは、threadidやtaskidなどのメタデータが含まれます。メタデータを除去するには、include_metaをfalseに設定します。

source
Profile.retrieve — Function
retrieve(; kwargs...) -> data, lidict

プロファイリング結果を移植可能な形式で「エクスポート」します。すべてのバックトレース（data）と、data 内の（セッション固有の）命令ポインターを、ファイル名、関数名、行番号を格納した LineInfo 値に対応付ける辞書を返します。この関数を使うと、プロファイリング結果を保存して後から分析できます。

source
Profile.callers — Function
callers(funcname, [data, lidict], [filename=<filename>], [linerange=<start:stop>])::Vector{Tuple{count, lineinfo}}

以前のプロファイリング実行の結果をもとに、特定の関数の呼び出し元を調べます。ファイル名（および、必要に応じて関数が定義されている行番号の範囲）を指定すると、オーバーロードされたメソッドを区別できます。戻り値は、呼び出し回数と呼び出し元の行情報を含むベクトルです。retrieve から取得したバックトレース data を指定することもできます。指定しない場合は、現在の内部プロファイルバッファが使用されます。

source
Profile.clear_malloc_data — Function
clear_malloc_data()

julia を --track-allocation 付きで実行すると、保存されているメモリ割り当てデータがすべて消去されます。テストしたいコマンドを実行して（JIT コンパイルを強制するため）、その後 clear_malloc_data を呼び出します。次に、コマンドをもう一度実行してから Julia を終了し、生成された *.mem ファイルを確認します。

Memory profiling

Profile.Allocs.@profile — Macro
Profile.Allocs.@profile [sample_rate=0.1] expr

expr の実行中に発生したメモリ割り当てをプロファイルし、結果と AllocResults 構造体の両方を返します。

サンプリングレートが 1.0 の場合はすべてを記録し、0.0 の場合は何も記録しません。

julia> Profile.Allocs.@profile sample_rate=0.01 peakflops()
1.03733270279065e11

julia> results = Profile.Allocs.fetch()

julia> last(sort(results.allocs, by=x->x.size))
Profile.Allocs.Alloc(Vector{Any}, Base.StackTraces.StackFrame[_new_array_ at array.c:127, ...], 5576)

詳しくは、Julia ドキュメントのプロファイリングチュートリアルを参照してください。

Julia 1.11

古いバージョンの Julia では、すべてのケースで型を取得できるわけではありませんでした。古いバージョンの Julia で、型 Profile.Allocs.UnknownType の割り当てが表示された場合、プロファイラーは割り当てられたオブジェクトの型を特定できていません。これは主に、コンパイラーが生成したコードから割り当てが発生した場合に起こります。詳しくは issue #43688 を参照してください。

Julia 1.11 以降では、すべての割り当てについて型が報告されるはずです。

Julia 1.8

割り当てプロファイラーは Julia 1.8 で追加されました。

Heap Snapshots

Profile.take_heap_snapshot — Function
Profile.take_heap_snapshot(filepath::String, all_one::Bool=false;
                           redact_data::Bool=true, streaming::Bool=false)
Profile.take_heap_snapshot(all_one::Bool=false; redact_data:Bool=true,
                           dir::String=nothing, streaming::Bool=false)

ヒープのスナップショットを、Chrome DevTools の Heap Snapshot ビューアーが想定する JSON 形式（拡張子は .heapsnapshot）で、デフォルトではカレントディレクトリ内のファイル $pid_$timestamp.heapsnapshot に書き込みます。カレントディレクトリに書き込めない場合は tempdir に書き込みます。指定があれば dir、指定されたフルパス、または IO ストリームに書き込みます。

all_one が true の場合、オブジェクトを簡単に数えられるよう、すべてのオブジェクトのサイズを 1 として記録します。それ以外の場合は、実際のサイズを記録します。

redact_data が true（デフォルト）の場合、オブジェクトの内容は出力しません。

streaming が true の場合、スナップショットデータをストリーミングし、filepath をプレフィックスとして 4 つのファイルに出力します。これにより、スナップショット全体をメモリ上に保持せずに済みます。これらのファイルは、Profile.HeapSnapshot.assemble_snapshot() を呼び出すことで再構成できます。この処理はオフラインで実行できます。

注意：パフォーマンス上の理由から、streaming=true を強く推奨します。分割されたファイルからスナップショットを再構成するには、スナップショット全体をメモリ上に保持する必要があります。そのため、スナップショットが大きい場合、処理中にメモリ不足になる可能性があります。ストリーミングを使えば、ワークロードの実行が終わった後にオフラインで再構成できます。streaming=false（デフォルト。後方互換性のため）でスナップショットを取得しようとしてプロセスが強制終了された場合、分割ファイルは常に指定した filepath と同じディレクトリに保存されます。そのため、後から assemble_snapshot() を使ってスナップショットを再構成できます。

source

The methods in Profile are not exported and need to be called e.g. as Profile.take_heap_snapshot().

julia> using Profile

julia> Profile.take_heap_snapshot("snapshot.heapsnapshot")

Traces and records julia objects on the heap. This only records objects known to the Julia garbage collector. Memory allocated by external libraries not managed by the garbage collector will not show up in the snapshot.

To avoid OOMing while recording the snapshot, we added a streaming option to stream out the heap snapshot into four files,

julia> using Profile

julia> Profile.take_heap_snapshot("snapshot"; streaming=true)

where "snapshot" is the filepath as the prefix for the generated files.

Once the snapshot files are generated, they could be assembled offline with the following command:

julia> using Profile

julia> Profile.HeapSnapshot.assemble_snapshot("snapshot", "snapshot.heapsnapshot")

The resulting heap snapshot file can be uploaded to chrome devtools to be viewed. For more information, see the chrome devtools docs. An alternative for analyzing Chromium heap snapshots is with the VS Code extension ms-vscode.vscode-js-profile-flame.

The Firefox heap snapshots are of a different format, and Firefox currently may not be used for viewing the heap snapshots generated by Julia.
