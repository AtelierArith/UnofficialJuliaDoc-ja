Tasks

Core.Task — Type
Task(func[, reserved_stack::Int])

指定された関数 func（引数なしで呼び出せる必要があります）を実行するための Task（コルーチン）を作成します。この関数が戻るとタスクは終了します。タスクは、作成時に親から引き継いだ「ワールドエイジ」で実行されます。scheduled

省略可能な引数 reserved_stack は、このタスクで使用できるスタックのサイズをバイト単位で指定します。デフォルトの 0 では、システムに応じたデフォルトのスタックサイズが使用されます。

Warning

デフォルトでは、タスクの sticky ビットは true に設定されます t.sticky。これは @async の従来のデフォルト動作を再現するものです。sticky タスクは、最初にスケジュールされたワーカースレッドでのみ実行できます。また、スケジュールされると、そのタスクをスケジュールしたタスクも sticky になります。Threads.@spawn の動作にするには、sticky ビットを手動で false に設定します。

Examples

julia> a() = sum(i for i in 1:1000);

julia> b = Task(a);

この例では、b は、まだ開始されていない実行可能な Task です。

Base.@async — Macro
@async

式をTaskで囲み、ローカルマシンのスケジューラキューに追加します。

値は@async内に$を使って補間できます。これにより、値が構築される基底クロージャに直接コピーされます。そのため、変数の値を挿入でき、非同期コードを現在のタスクにおける変数の値の変更から切り離せます。

Warning

特に一般公開されるライブラリでは、並列処理が不要な場合でも、常に@asyncよりThreads.@spawnを優先することを強く推奨します。これは、現行のJulia実装では、@asyncを使うと、親タスクがワーカースレッド間を移動できなくなるためです。そのため、ライブラリ関数内での一見無害な@asyncの使用が、ユーザーアプリケーションのまったく別の部分のパフォーマンスに大きな影響を及ぼすことがあります。

Julia 1.4

$による値の補間は、Julia 1.4以降で利用できます。

Base.asyncmap — Function
asyncmap(f, c...; ntasks=0, batch_size=nothing)

複数のタスクを並行して使用し、コレクション（または長さが等しい複数のコレクション）に対して f を適用します。複数のコレクションを引数に指定した場合、f は要素ごとに適用されます。

出力の順序は、コレクションの要素の順序 c と同じになることが保証されています。

ntasks は、並行して実行するタスク数を指定します。コレクションの長さに応じて、ntasks が指定されていない場合、並行マッピングには最大100個のタスクが使用されます。

ntasks には、引数を取らない関数を指定することもできます。この場合、各要素の処理前に並列実行するタスク数が確認され、ntasks_func の値が現在のタスク数を上回っていれば、新しいタスクが開始されます。

batch_size を指定すると、コレクションはバッチモードで処理されます。この場合、f は、引数タプルの Vector を受け取り、結果のベクトルを返す関数でなければなりません。入力ベクトルの長さは batch_size 以下です。

以下の例では、マッピング関数が実行されたタスクの objectid を返すことで、異なるタスクでの実行を示します。

まず、ntasks を指定しない場合、各要素はそれぞれ異なるタスクで処理されます。

julia> tskoid() = objectid(current_task());

julia> asyncmap(x->tskoid(), 1:5)
5-element Vector{UInt64}:
 0x6e15e66c75c75853
 0x440f8819a1baa682
 0x9fb3eeadd0c83985
 0xebd3e35fe90d4050
 0x29efc93edce2b961

julia> length(unique(asyncmap(x->tskoid(), 1:5)))
5

ntasks=2 を指定すると、すべての要素が2つのタスクで処理されます。

julia> asyncmap(x->tskoid(), 1:5; ntasks=2)
5-element Vector{UInt64}:
 0x027ab1680df7ae94
 0xa23d2f80cd7cf157
 0x027ab1680df7ae94
 0xa23d2f80cd7cf157
 0x027ab1680df7ae94

julia> length(unique(asyncmap(x->tskoid(), 1:5; ntasks=2)))
2

batch_size を指定した場合、マッピング関数は引数タプルの配列を受け取り、結果の配列を返すように変更する必要があります。変更後のマッピング関数では、これを実現するために map を使用します。

julia> batch_func(input) = map(x->string("args_tuple: ", x, ", element_val: ", x[1], ", task: ", tskoid()), input)
batch_func (generic function with 1 method)

julia> asyncmap(batch_func, 1:5; ntasks=2, batch_size=2)
5-element Vector{String}:
 "args_tuple: (1,), element_val: 1, task: 9118321258196414413"
 "args_tuple: (2,), element_val: 2, task: 4904288162898683522"
 "args_tuple: (3,), element_val: 3, task: 9118321258196414413"
 "args_tuple: (4,), element_val: 4, task: 4904288162898683522"
 "args_tuple: (5,), element_val: 5, task: 9118321258196414413"

Core.ConcurrencyViolationError — Type
ConcurrencyViolationError(msg) <: Exception

並行処理のセマンティクスに対する検出可能な違反が発生したときにスローされるエラーです。

このエラーが使われるケースの例を、以下にいくつか示します（すべてを網羅しているわけではありません）。

  • デッドロックが検出されたときにスローする（例：wait(current_task())）
  • 安全でないことが既知の動作を試みたとき（例：yield(current_task)）
  • スレッドセーフでないことが既知のデータ構造を、複数の並行タスクから変更しようとしたとき
  • このタスクがロックしていないロックを解除しようとしたとき

Base.yield — Function
yield(t::Task, arg = nothing)

スケジューラを呼び出す前に、ただちにtへ譲る、schedule(t, arg); yield()の高速な非公平スケジューリング版です。

tが現在実行中のタスクである場合、ConcurrencyViolationErrorをスローします。

source
yield()

スケジューラに切り替えて、別のスケジュール済みタスクを実行できるようにします。この関数を呼び出したタスクは引き続き実行可能な状態にあり、ほかに実行可能なタスクがなければ直ちに再開されます。

source
Base.yieldto — Function
yieldto(t::Task, arg = nothing)

指定されたタスクに切り替えます。初めてそのタスクに切り替えるときは、タスクの関数が引数なしで呼び出されます。2 回目以降の切り替えでは、そのタスクで最後に行われた yieldto の呼び出しから arg が返されます。これはタスクの切り替えのみを行う低レベルの呼び出しであり、状態やスケジューリングは一切考慮しません。使用は推奨されません。

source
Base.sleep — Function
sleep(seconds)

現在のタスクを指定した秒数だけブロックします。最小スリープ時間は1ミリ秒、または0.001の入力です。

source
Base.schedule — Function
schedule(t::Task, [val]; error=false)

Task をスケジューラのキューに追加します。これにより、システムがほかの処理を行っていない間、タスクは常に実行されます。ただし、wait のようなブロッキング操作をタスクが実行する場合は除きます。

2 番目の引数 val が指定されている場合、タスクが再び実行されるときに、その引数が（yieldto の戻り値を介して）タスクに渡されます。error が true の場合、その値は起床したタスク内で例外として送出されます。

Warning

すでに開始されている任意の Task に対して schedule を使用するのは誤りです。詳しくは the API reference を参照してください。

Warning

デフォルトでは、タスクの sticky bit は true t.sticky に設定されます。これは、@async の従来のデフォルト動作を再現するものです。sticky タスクは、最初にスケジュールされたワーカースレッドでのみ実行できます。また、スケジュールされると、そのタスクをスケジュールしたタスクも sticky になります。Threads.@spawn の動作にするには、sticky bit を手動で false に設定してください。

Examples

julia> a5() = sum(i for i in 1:1000);

julia> b = Task(a5);

julia> istaskstarted(b)
false

julia> schedule(b);

julia> yield();

julia> istaskstarted(b)
true

julia> istaskdone(b)
true

Base.wait — Function
wait([x])

イベントが発生するまで、現在のタスクをブロックします。

  • Channel: チャネルに値が追加されるまで待機します。
  • Condition: 条件が満たされるまでnotifyを待機し、notifyに渡されたvalパラメーターを返します。正確な動作については、waitのCondition固有のdocstringを参照してください。
  • Process: プロセスまたはプロセスチェーンが終了するまで待機します。成功したか失敗したかは、プロセスのexitcodeフィールドで確認できます。
  • Task: Taskが終了するまで待機します。正確な動作については、waitのTask固有のdocstringを参照してください。
  • RawFD: ファイルディスクリプターの変更を待機します（FileWatchingパッケージを参照）。

引数を渡さない場合、タスクは期間を定めずにブロックされます。タスクを再開できるのは、scheduleまたはyieldtoを明示的に呼び出した場合のみです。

待機中の条件が満たされてから処理を続行できるよう、waitは多くの場合、whileループ内で呼び出されます。

source
Base.waitany — Function
waitany(tasks; throw=true) -> (done_tasks, remaining_tasks)

指定されたタスクのうち、少なくとも1つが完了するまで待機します。

throw が true の場合、完了したタスクのいずれかが例外を伴って終了すると、CompositeException をスローします。

戻り値は2つのタスクベクトルで構成されます。1つ目は完了したタスク、もう1つは未完了のタスクです。

Warning

呼び出すたびに tasks のリストを走査し、各タスクと同期する必要があるため、タスクごとに個別のタスクを作成して直列に実行するコードと比べて、性能が大きく低下する可能性があります。代わりに waitall(tasks; failfast=true) の使用も検討してください。

Julia 1.12

この関数を使用するには、Julia 1.12 以降が必要です。

source
Base.waitall — Function
waitall(tasks; failfast=true, throw=true) -> (done_tasks, remaining_tasks)

指定されたすべてのタスクが完了するまで待機します。

failfast が true の場合、指定されたタスクのうち少なくとも1つが例外によって終了すると、この関数は戻ります。throw が true の場合、完了したタスクのいずれかが失敗すると、CompositeException をスローします。

failfast と throw のキーワード引数は、それぞれ独立して機能します。throw=true のみを指定した場合、この関数はすべてのタスクが完了するまで待機します。

戻り値は2つのタスクベクトルからなります。1つ目には完了したタスクが、もう1つには未完了のタスクが含まれます。

Base.Condition — Type
Condition()

タスクが待機できる、エッジトリガー型のイベントソースを作成します。Condition に対して wait を呼び出したタスクは、一時停止されてキューに追加されます。その後、Condition に対して notify を呼び出すと、待機中のタスクが起こされます。notify の省略可能な引数を使用すると、条件の待機から値が返されたり、エラーが発生したりすることがあります。エッジトリガーでは、notify の呼び出し時点で待機しているタスクだけが起こされます。レベルトリガー型の通知を実現するには、通知が発生したかどうかを追跡するための状態を別途保持する必要があります。Channel 型と Threads.Event 型はこの処理を行うため、レベルトリガー型イベントに使用できます。

このオブジェクトはスレッドセーフではありません。スレッドセーフなバージョンについては、Threads.Condition を参照してください。

source
Base.Threads.Condition — Type
Threads.Condition([lock])

Base.Condition のスレッドセーフ版です。

Threads.Condition に対して wait または notify を呼び出すには、まずそのオブジェクトに対して lock を呼び出す必要があります。wait を呼び出すと、ブロック中はロックがアトミックに解放され、wait が戻る前に再取得されます。そのため、Threads.Condition c の慣用的な使い方は次のようになります。

lock(c)
try
    while !thing_we_are_waiting_for
        wait(c)
    end
finally
    unlock(c)
end
Julia 1.2

この機能を使用するには、Julia 1.2 以降が必要です。

source
Base.Event — Type
Event([autoreset=false])

レベルトリガー型のイベントソースを作成します。Eventに対してwaitを呼び出したタスクは、Eventに対してnotifyが呼び出されるまで、一時停止してキューに入れられます。notifyが呼び出されると、Eventはシグナル状態を保ち、その後はresetが呼び出されるまで、待機中のタスクがブロックされなくなります。

autoresetがtrueの場合、notifyを呼び出すたびに、waitから解放されるタスクは最大1つです。

これにより、notify/waitに対してacquireおよびreleaseのメモリ順序が保証されます。

Julia 1.1

この機能を使用するには、Julia 1.1以降が必要です。

Julia 1.8

autoresetの機能とメモリ順序の保証を使用するには、Julia 1.8以降が必要です。

Base.notify — Function
notify(condition, val=nothing; all=true, error=false)

条件を待っているタスクを起こし、valを渡します。allがtrue（デフォルト）の場合は、待機中のタスクをすべて起こします。それ以外の場合は、1つだけ起こします。errorがtrueの場合、渡された値は起こされたタスク内で例外として送出されます。

Base.ReentrantLock — Type
ReentrantLock()

Taskを同期するための再入可能ロックを作成します。同じタスクは、必要な回数だけロックを取得できます（名前に「再入可能」とあるのはこのためです）。各lockには、対応するunlockが必要です。

lockを呼び出すと、対応するunlockが呼び出されるまで、そのスレッドでファイナライザーが実行されなくなります。以下に示す標準的なロックパターンは通常どおり使用できますが、tryとlockの順序を逆にしたり、tryブロック自体を省略したりしないよう注意してください（たとえば、ロックを保持したままreturnしようとする場合など）。

ロックおよびロック解除の呼び出しでは、acquire/releaseメモリ順序が保証されます。

lock(l)
try
    <atomic work>
finally
    unlock(l)
end

!islocked(lck::ReentrantLock)が成立する場合、ほかのタスクが「同時に」ロックを取得しようとしていなければ、trylock(lck)は成功します。

source

    expr
finally

これは、do ブロックを指定して lock を使う場合と似ていますが、クロージャを作成しないため、パフォーマンスが向上することがあります。

Low-level synchronization using schedule and wait

The easiest correct use of schedule is on a Task that is not started (scheduled) yet. However, it is possible to use schedule and wait as a very low-level building block for constructing synchronization interfaces. A crucial pre-condition of calling schedule(task) is that the caller must "own" the task; i.e., it must know that the call to wait in the given task is happening at the locations known to the code calling schedule(task). One strategy for ensuring such pre-condition is to use atomics, as demonstrated in the following example:

@enum OWEState begin
    OWE_EMPTY
    OWE_WAITING
    OWE_NOTIFYING
end

mutable struct OneWayEvent
    @atomic state::OWEState
    task::Task
    OneWayEvent() = new(OWE_EMPTY)
end

function Base.notify(ev::OneWayEvent)
    state = @atomic ev.state
    while state !== OWE_NOTIFYING
        # Spin until we successfully update the state to OWE_NOTIFYING:
        state, ok = @atomicreplace(ev.state, state => OWE_NOTIFYING)
        if ok
            if state == OWE_WAITING
                # OWE_WAITING -> OWE_NOTIFYING transition means that the waiter task is
                # already waiting or about to call `wait`. The notifier task must wake up
                # the waiter task.
                schedule(ev.task)
            else
                @assert state == OWE_EMPTY
                # Since we are assuming that there is only one notifier task (for
                # simplicity), we know that the other possible case here is OWE_EMPTY.
                # We do not need to do anything because we know that the waiter task has
                # not called `wait(ev::OneWayEvent)` yet.
            end
            break
        end
    end
    return
end

function Base.wait(ev::OneWayEvent)
    ev.task = current_task()
    state, ok = @atomicreplace(ev.state, OWE_EMPTY => OWE_WAITING)
    if ok
        # OWE_EMPTY -> OWE_WAITING transition means that the notifier task is guaranteed to
        # invoke OWE_WAITING -> OWE_NOTIFYING transition. The waiter task must call
        # `wait()` immediately. In particular, it MUST NOT invoke any function that may
        # yield to the scheduler at this point in code.
        wait()
    else
        @assert state == OWE_NOTIFYING
        # Otherwise, the `state` must have already been moved to OWE_NOTIFYING by the
        # notifier task.
    end
    return
end

ev = OneWayEvent()
@sync begin
    Threads.@spawn begin
        wait(ev)
        println("done")
    end
    println("notifying...")
    notify(ev)
end

# output
notifying...
done

OneWayEvent lets one task to wait for another task's notify. It is a limited communication interface since wait can only be used once from a single task (note the non-atomic assignment of ev.task)

In this example, notify(ev::OneWayEvent) is allowed to call schedule(ev.task) if and only if it modifies the state from OWE_WAITING to OWE_NOTIFYING. This lets us know that the task executing wait(ev::OneWayEvent) is now in the ok branch and that there cannot be other tasks that try to schedule(ev.task) since their @atomicreplace(ev.state, state => OWE_NOTIFYING) will fail.
