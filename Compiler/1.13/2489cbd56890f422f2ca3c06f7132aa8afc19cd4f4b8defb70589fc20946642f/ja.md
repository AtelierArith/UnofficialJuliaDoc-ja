```julia
ir_inline_unionsplit!
```

この関数の主な目的は、ユニオン分割されたディスパッチ候補のシグネチャに対応するフラットな`isa`チェックを生成し、ディスパッチの動作をエミュレートすることです。これらのチェックにより、各メソッド本体を対応する`isa`条件ブロックにインライン展開できます。

このエミュレーションを正しく機能させるには、次の2つの前提条件が必要です。

1. ディスパッチ候補の順序

ディスパッチ候補は、具体性の高い順に処理する必要があります。生成される`isa`チェックにもこの順序を反映させなければなりません。特に、メソッドシグネチャが具象型とは限らないためです。たとえば、次のメソッドがあるとします。

```julia
f(x::Int)    = ...
f(x::Number) = ...
f(x::Any)    = ...
```

呼び出し箇所`f(x::Any)`に対する、`isa`に基づく正しいディスパッチのエミュレーションは、次のようになります。

```julia
if isa(x, Int)
    [inlined/resolved f(x::Int)]
elseif isa(x, Number)
    [inlined/resolved f(x::Number)]
else
    [inlined/resolved f(x::Any)]
end
```

`ml_matches`は、曖昧なケースを除けば、マッチしたメソッド候補をすでに正しくソートしているはずです。曖昧なケースは、この段階までにすでに除外しています。

2. 型の等価性制約

型変数によって課される型の等価性制約も考慮する必要があります。単純な`isa`チェックだけでは、場合によっては意味を正しく表現できません。たとえば、次のメソッド定義があるとします。

```julia
g(x::T, y::T) where T<:Integer = ...
```

この場合、呼び出し箇所`g(x::Any, y::Any)`を次のように最適化するのは*不正*です。

```julia
if isa(x, Integer) && isa(y, Integer)
    [inlined/resolved g(x::Integer, y::Integer)]
else
    g(x, y) # fallback dynamic dispatch
end
```

`x`と`y`が同じ型であることも確認する必要があるためです。

ただし、このようなケースは、この段階までに主に`case.sig::UnionAll`を除外することで、すでに取り除いています。そのため、ここで型の等価性を気にする必要はありません。

つまり、ディスパッチ候補は順番に処理できます。その際、`ml_matches`で候補を検出した後も、その順序が保たれることを前提とします。
